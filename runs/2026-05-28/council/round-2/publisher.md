# Round 2 — senior-publisher (세부 수치 단일 확정)

## 다른 4명 수치 보고 입장

Round 1에서 5명 방향 일치. 이제 단일 포맷 확정. 퍼블리셔는 JSON 섹션 스키마·렌더 안전성 관점에서 두 가지만 못 박으면 나머지는 동의.

## 확정 안건별 입장

### 1. 목표 분량 단일값 — 본문 3,000자 권장 / 3,500자 절대 상한
- 입장: ✓ +2
- 근거: 화면 스캔성 기준 모바일 스크롤 2~3회. 3,000 권장/3,500 상한이면 인용 링크줄·코드 조건이 들어가는 DEV도 커버된다. 동의.

### 2. JSON 섹션 스키마는 안 건드린다 — 블록 수만 줄인다 (퍼블리셔 핵심 조건)
- 입장: ✓ +2
- 근거: `article-section is-bullet-summary` + `is-deep-dive` 2섹션 구조, `block.kind`(list/quote/subhead/paragraph) 4종은 그대로 둔다. 바꾸는 건 *블록 개수*뿐 — subhead 블록 4→2, paragraph 블록 6~8→3~4, list(점검질문) 3→1, 인용은 paragraph가 아니라 마지막 paragraph(관련자료 링크줄)로. 스키마·Vue 렌더·파서·Storybook 컴포넌트 무수정. 이게 안전한 적용의 핵심.

### 3. DEV 인용 3종 = `관련 자료` 링크 줄 (paragraph 블록 1개, 라벨 3줄)
- 입장: ✓ +2
- 근거: 직전 council 결정3 "세 줄 모두 필수"는 *링크 라벨 3줄*로 충족. 본문 산문에서 빼고 인사이트 마지막 paragraph 블록에 `관련 자료:` + `[합성 데모] / [공식 사양] / [프로덕션 사례]` 3줄. source-verifier가 검증하는 3종 정보는 100% 보존, 본문 산문 단락은 즉시 사라진다.

### 4. DEV 마지막 블록 표준 = `관련 자료` 링크줄 (옵션 `같이 보면 좋은 기술`도 여기로 흡수)
- 입장: ✓ +2
- 근거: DEV는 점검 질문 없음. 마지막 블록은 인용 3종 링크줄로 통일. 기존 `같이 보면 좋은 기술(옵션)` subhead는 폐기하고 링크줄에 흡수. 소제목 1개 추가 절감.

### 5. DEV 한국 4축 = `구현 관점` 안 한 문장 유지
- 입장: ✓ +2
- 근거: "iOS Safari 미지원 — @supports 폴백 필수" 류는 퍼블리셔가 가장 먼저 보는 정보. 별도 단락 아니라 `구현 관점` 단락 안 한 문장으로 박으면 분량 부담 0. 유지 확정.

### 6. 요약 불릿 — 3~5개, DEV 첫 2불릿 기술명·조건 강제 유지
- 입장: ✓ +2
- 근거: 3~5개 동의. DEV는 첫 두 불릿에 기술명·API·브라우저·접근성 조건 중 하나 이상(기존 룰) 보존. 개수만 줄고 정보 밀도 룰은 유지.

## 다음 회의에 들고 갈 단 하나
**JSON 스키마·블록 kind는 무수정, 블록 개수만 줄인다 + DEV 인용 3종은 마지막 `관련 자료` 링크줄(라벨 3줄)** — 적용이 안전하고 source-verifier 검증도 그대로 돈다.
