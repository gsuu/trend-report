### 18. Figma 데스크톱 디버그 모드만으로 Claude를 디자인 작업에 붙이는 방법

- 날짜: 2026-02-25
- 태그: `Figma` `CLAUDE.md` `개인 디자인 에이전트` `디자인 시스템`
- 국가: GLOBAL
- 카테고리: design/system
- 직무 태그: `웹디자인` `웹DEV`
- 출처 유형: guide
- 출처: Into Design Systems (Sil Bormüller)
- 출처 URL: https://www.intodesignsystems.com/blog/claude-code-figma-no-mcp
- 이미지: https://www.intodesignsystems.com/og-image-claude-code-figma.png
- 이미지 설명: Into Design Systems 본문 og:image — `claude` CLI가 Figma 데스크톱과 연결된 화면
- 요약: Figma 데스크톱의 Chrome DevTools 디버그 모드를 활용해 API 키와 MCP 설정 없이 1분 안에 Claude를 붙이고, `CLAUDE.md`에 작업 패턴을 학습시켜 개인 디자인 에이전트로 키우는 방법을 정리한 가이드.

##### 요약

- GitHub의 `figma-cli` 저장소를 받은 뒤 터미널에서 해당 폴더로 이동해 `claude` 명령을 실행하고, 첫 메시지로 `Setup: install dependencies and connect to Figma`만 입력하면 약 1분 안에 Figma 데스크톱과 연결된다. API 키 발급이나 JSON 설정은 필요하지 않다.
- 연결의 작동 원리는 Figma 데스크톱이 내장한 Chrome DevTools 디버그 모드를 통해 로컬에서 직접 통신하는 방식이다. Figma 세션이 이미 인증돼 있어 별도 토큰을 주고받지 않고, 무료 Figma 계정에서도 동작한다.
- 작업 폴더의 `CLAUDE.md` 파일을 에이전트의 메모리로 쓴다. 레이어 네이밍 규칙, 선호 간격과 정렬, 페이지·프레임 구조, 내보내기 설정, 반복 작업 순서를 한 번 보여주고 저장해두면 다음부터는 같은 방식으로 작업을 반복한다.
- 공식 MCP 방식과 비교했을 때 설정 시간이 짧고 토큰 소비가 줄어든다. 다만 글쓴이는 본문 말미에 "work in progress"라고 명시하며 사용자 피드백을 받아 개선 중인 단계라고 덧붙였다.

##### 디자인 인사이트

> 도구를 빠르게 붙이는 것보다, 무엇을 `CLAUDE.md`에 적어둘지 정하는 일이 먼저다.

###### 왜 참고할 만한가

이 글은 새 도구를 소개하는 글이라기보다 "개인용 디자인 에이전트를 어떻게 키우느냐"에 대한 방법론에 가깝다. 핵심은 두 줄로 줄어든다. 첫째, Figma 데스크톱이 내부적으로 Chrome DevTools를 갖고 있다는 점을 활용하면 MCP 같은 별도 프로토콜 없이도 로컬에서 디자인 도구와 LLM을 묶을 수 있다는 것. 둘째, 한 번 보여준 작업 패턴을 `CLAUDE.md`라는 마크다운 한 장에 누적시키면 그것 자체가 개인 디자인 시스템의 시작점이 된다는 것.

###### 어디에 적용할 수 있을까

당장 디자인팀 전체 워크플로우를 바꿀 만한 단계는 아니다. 대신 디자이너 한 명이 자기 시안 정리, 레이어 네이밍 통일, 반복되는 내보내기 설정 같은 자잘한 작업을 줄여보려는 실험에 쓰기 좋다. 적용 단위는 "팀 전체"가 아니라 "내 작업 폴더"부터다. 사내 디자인 토큰이나 컴포넌트 명세를 무리해서 통째로 옮기기보다, 자주 깨지던 네이밍 규칙·간격·아이콘 사이즈처럼 "이 사람이 자꾸 잊는 것"부터 한 줄씩 적어두는 방식이 안전하다.

###### 디자인 관점

`CLAUDE.md`에 무엇을 적느냐가 그대로 에이전트의 결과물이 된다. 사내 디자인 시스템과 충돌하지 않으려면 옮길 항목과 옮기지 말아야 할 항목을 나눠 적는 것이 먼저다. 옮기기 좋은 항목은 레이어 네이밍 규칙, 자주 쓰는 spacing 토큰의 별칭, 내보내기 포맷처럼 "값이 정해져 있고 변동이 적은 것"이다. 옮기지 않는 편이 나은 항목은 컬러 토큰의 의미 매핑, 컴포넌트 variant 규칙처럼 디자인 시스템 본진과 충돌이 생기면 잡기 어려운 부분이다. 후자는 사내 시스템 문서를 단일 출처로 두고, `CLAUDE.md`에는 "이 항목은 시스템 문서를 따른다"는 한 줄 참조만 남기는 편이 안전하다.

###### 점검 질문

내 `CLAUDE.md`에 쌓인 패턴 중 사내 디자인 시스템 본진과 충돌할 가능성이 있는 항목은 어떤 것이고, 시스템이 갱신될 때 이 파일은 누가 어느 주기로 같이 갱신해야 하나.
