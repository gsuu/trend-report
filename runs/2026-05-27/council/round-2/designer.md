## (1) 합의 6개 (A~F) 최종 사인

### A. references/{design,service,dev}.md ★ → 매거진 본문 자동 승격
- **✓ 그대로 사인**. 내가 Round 1에서 가장 먼저 박은 안건 — 5/5 합의로 굳음. 운영 위치(Phase 4 또는 Phase 6 직전)도 종합본대로면 문제 없음. 다만 area별 *호당 최소 1건*은 유지 권장 — "있으면 가져온다"가 아니라 "★이 있을 때는 무조건 후보 풀에 들어간다"가 핵심. 글쓰기 단계에서 다른 후보가 더 강하면 ★이 *최종 채택* 안 될 수는 있음(메모리 룰 일치).

### B. 한국 응용·한국 환경 필수 게이트
- **✓ 그대로 사인** + *경량화 1줄 수정 제안*. 종합본의 "한국 응용 단락 + 한국 클라이언트명 1개 이상" 게이트는 동의하되, *디자이너 시점에서 보면 "한국 클라이언트명 1개" 기준이 너무 좁아 보일 수 있음* — 시즌 컬러축·문화기관(LIDO)·글로벌 캠페인 케이스 같은 글은 *한국 클라이언트 이름이 본문에 직접 박히지 않아도 응용처 단락에 "이 컬러 보드는 무신사·29CM 26 S/S 시즌 키비주얼 결정 단계에 인용 가능"*이 들어가면 통과. **수정 권고**: "한국 클라이언트명 1개 이상 + *한국 응용 단락 한 문장*"으로 OR 게이트화. 응용 단락에 클라이언트 이름이 박힌 게 가장 강하지만, 응용 시나리오만 있어도 통과 가능.
- publisher의 dev 4축(iOS Safari·한글 폰트·모바일·접근성)은 dev 카테고리에만 적용되는 것으로 명시 — design/service에는 다른 축이라 4축 강제는 dev에 한정.

### C. 인용 표준 (결정 근거 + 프로덕션 사례 + 공식 사양 3종)
- **✓ 그대로 사인** (디자이너 시점에서도 강하게 지지). 단 *카테고리별 해석 분리*가 명시되어야 함:
  - **dev**: 합성 데모/한국 컨텍스트 + 공식 사양(MDN/W3C) + 프로덕션 사례 (publisher·tf-leader 안건 그대로)
  - **design**: *결정-근거 한 단락* (디렉터/메이커 quote·process·왜 이 선택) + *시각적 출처 1차* (자사 캠페인 페이지·디자이너 본인 포트폴리오) + *응용 후보 단락*
  - **service**: *한국 라이브 정책 본문* + *글로벌 비교 1건*(tf-leader 안건) + *PM 회의 직행 응용 후보*
- 디자이너 카테고리는 "프로덕션 사례"가 dev와 의미가 달라 — *production = 실제 라이브 사이트·캠페인 페이지*. 종합본에 *카테고리별 인용 3종 정의*를 별도 표로 정리 권고.

### D. 새 채널/시드 추가
- **✓ 그대로 사인**. 내 안건 3(무신사 SeedDesign·29CM 매거진·아모레 STORIES·올리브영·SSF·LF몰 6채널) + planner P5(한국 패션·뷰티 정책 발신처 + BoF·Retail Dive·Glossy) + trend-hunter C(무신사 뉴스룸·CJ뉴스룸·careet·패션비즈·mobiinside) + tf-leader 3(분기 1회 브랜드 자사 사이트 직접 탐색) — 네 갈래가 *서로 보완*. 한 패치로 합쳐서 진행. 단 *제외 명시* 누락 금지(trend-hunter가 지적한 platform 403·longblack 유료·outstanding.kr 매칭 0).

### E. trend-radar 매거진 본문에 한국 시장 맥락 인용 의무

## (2) 충돌 G 결정

**선택: 옵션 1 (비율 X, *슬롯만 신설*)**

**사유**:
1. 메모리 룰(`feedback_curation_no_quota.md`) "호당 비율·수량 할당 금지 — 좋은 글이면 다 싣고, 좋은 글이 없으면 비운다"가 명시적. 내가 Round 1에서 +1 던진 "service 5 / design 4 / dev 3"은 *비율 강제*가 아니라 *후보 풀의 무게중심 가이드*라는 단서를 달았지만, 글 단위 룰로 해석되면 메모리 룰 위반.
2. trend-hunter 안건 B의 표현이 정확 — *"수량 quota가 아니라 도메인 quota"* / *"없으면 비운다는 원칙은 유지하면서 있을 때 어디서 가져오는가의 우선순위만 박는다"*. 비율보다는 *후보 풀에서의 우선순위 가산점*으로 풀어야 메모리 룰과 호환.
3. 따라서 내 Round 1 안건 4는 *옵션 1로 재해석*: ★ 후보가 있는 카테고리에 *슬롯이 자동 신설*되되, 그 주에 ★이 없으면 슬롯 비움. dev는 *제외 패턴 4종*으로 약한 후보가 자동으로 빠지므로, 결과적으로 design·service로 자연 이동. *명시 비율 룰은 작성하지 않음*.

## (3) 미언급 안건 H/I/J 평가

### H. SERVICE 2-tier 서브태그 (frontline/system) — ⚠️ +1
- planner P3의 안건. 디자이너 시점에서 *부분 동의*. 매거진 #01 우아한공방 RAG처럼 *시스템 PM 글*과 *클라이언트 직행 멤버십·IA 글*이 같은 SERVICE 슬롯에서 섞이면 디자이너가 카드만 보고 *시안 직결 글*을 분간하기 어려운 건 사실.
- 단 *areaKey/categoryKey 단계 분리는 비용 큼*(`magazine.json` 스키마 변경 + 사이트 카드 컴포넌트 수정). **권고**: 1차로 *magazine-writer 출력 메타데이터에 `subAreaKey` 필드만 추가*하고 사이트 카드 UI 변경은 *2-3회차 누적 후 분포 보고 결정*. 분포가 frontline 80% / system 20%로 한쪽 쏠림이면 굳이 UI 분리 안 해도 됨.
- 디자이너 시점에서는 *system 글이 디자인시스템 운영자에게는 frontline*인 경우가 많아(우아한공방 RAG가 그 예) frontline/system 이진 분리가 *디자이너의 글 발견 동선을 오히려 좁힐 위험*도 있음 — 그래서 ⚠️ 조건부.

### I. 분기별 market-brief 산출물 신규 — ✓ +1
- trend-hunter E의 안건. 디자이너 시점에서 *분기 시작 시점의 인트로 슬라이드 1장*은 가치 있음. 시안 회의·제안서 인트로에서 *"왜 지금 W컨셉 리뉴얼인가" / "왜 26 S/S 시즌 컬러가 Teal인가"*를 한 장으로 정리한 게 있으면 디자이너가 *그 한 장에서 시작*해 시안을 그릴 수 있음.
- 단 *분기 1회·1-2페이지 압축* 원칙은 지켜야 — 더 길어지면 *trend-radar 누적본*과 구분이 안 됨. trend-hunter 제안한 *상위 키워드 5개 + 정량 수치 5개 + 클라이언트별 응용 후보 5개* 포맷이 적정.
- 매거진·references와 *별도 라인*으로 운영 (제안서 인트로 직접용)이 명확하면 ✓.

### J. tf-leader 격주 자동 호출 + ★ 전수 비교 — ⚠️ +0
- tf-leader 본인이 ⚠️ 조건부로 던진 안건. 디자이너 시점에서도 *비용 vs 효과*가 애매.
- *효과*: 첫 회차 5건 비교에서 *4가지 구조적 결손* 발견 — 격주로 돌리면 누적 발견 효과 큼.
- *비용*: 시니어 미팅 자체가 5에이전트 병렬(시니어 3 + tf + trend) 토큰 부담 큼. *매번 senior-meeting에 tf-leader 자동 포함*은 운영 부담이 매주 누적.
- **권고**: 자동 호출 대신 *senior-meeting 산출물에 "이번 호 ★ 항목 N건 누적 — tf-leader 호출 권고 여부" 자동 판단 1줄*만 박고, 사용자가 *명시 트리거*로 호출하는 현 흐름 유지. 누적 ★이 임계(예: 8건) 넘으면 알림만. 정기 자동화는 1개월 운영 후 재검토.
- 점수 +0 — 안건 자체는 옳지만 *지금 박는 룰로는 약하다*. 메모리 누적 후 결정.

## Round 1 대비 입장 변화

1. **충돌 G 비율 안건 → 옵션 1로 명시 후퇴**. Round 1에서 *비율 가이드 +1*로 던졌지만 메모리 룰 직접 확인 + trend-hunter B의 *"도메인 quota는 OK·수량 quota는 NO"* 정리가 명확해 *수량 비율 룰은 작성하지 않음*으로 입장 정리. 결과적으로 dev 제외 패턴 + ★ 자동 승격으로 자연 재조정되는 흐름이 메모리 룰과 호환.
2. **B 게이트 경량화 제안 추가**. publisher의 dev 4축이 design/service에 그대로 적용되면 게이트가 너무 빡빡해질 위험 — *카테고리별 적용 분리*를 명시 권고로 추가. "한국 클라이언트명 1개" 기준도 *시즌 컬러축·문화기관 글*을 위해 *응용 단락 한 문장*과 OR 게이트화 제안.
3. **C 인용 표준 → 카테고리별 해석 표 분리 권고**. tf-leader·publisher가 dev 시점에서 정의한 *합성 데모 + 공식 사양 + 프로덕션 사례* 3종이 design·service에 그대로 옮기면 의미가 달라짐 — 카테고리별 *인용 3종의 의미*를 별도 표로 정리해야 magazine-writer 프롬프트가 혼란 없음.
4. **H 서브태그 → 메타데이터만 1차 도입 권고**. planner P3 동의하되 *UI 분리는 누적 후 결정*으로 신중화. 디자이너 시점에서 frontline/system 이진 분리가 *글 발견 동선을 좁힐 위험*도 봤기 때문.

## 마지막 보고

합의 6개 A~F 전 사인 (B는 한국 클라이언트명 OR 응용 단락 OR 게이트로 경량화, C는 카테고리별 인용 3종 표 분리 권고, F는 publisher 안건 1의 제외 4패턴 그대로 채택 권장). 충돌 G는 **옵션 1(비율 X, 슬롯만 신설)** 선택 — 메모리 룰 일치 + trend-hunter B의 도메인 quota 해석으로 재정리. 미언급 안건은 **H ⚠️ +1**(서브태그 1차는 메타데이터만, UI 분리는 누적 후) / **I ✓ +1**(분기별 market-brief 1-2페이지, 별도 라인) / **J ⚠️ +0**(자동 호출 대신 senior-meeting 산출물에 알림 1줄만, 정기 자동화는 1개월 후 재검토). 가장 큰 입장 변화는 *Round 1 비율 +1을 옵션 1로 후퇴*한 것 — 메모리 룰을 위반하지 않는 슬롯-기반 자동 재조정이 같은 효과를 메모리 룰과 호환되는 방식으로 달성.
