## 현재 본문 내용 인벤토리 (점검 자료)

매거진 글 한 편이 가진 콘텐츠 단위는 다음과 같다:

- **메타 라인** (header): 날짜·태그·국가·카테고리·직무 태그·출처 유형·출처·출처 URL·이미지·이미지 설명·요약·회의 질문·CodePen/...·이미지 2/3/...·흐름·변화 유형·브랜드.
- **takeaway·deck** (hero): h1 한 줄 결론 + 1~2문장 리드.
- **본문 섹션 (카테고리별 잠금셋):**
  - **SERVICE** — `##### 요약` (업데이트 / 서비스 맥락 / 변경 전 / 변경 후 / 수치·팩트) → `##### 매거진 인사이트` (왜 지금 이 업데이트인가 / 사용자는 무엇을 덜 해도 될까 / 설계 관점 / 점검 질문)
  - **Design** — `##### 요약` → `##### 디자인 인사이트` (왜 참고할 만한가 / 어디에 적용할 수 있을까 / 디자인 관점 / 점검 질문)
  - **DEV** — `##### 요약` → `##### 매거진 인사이트` (왜 지금 이 업데이트인가 / 구현 관점 / 실무에 어떻게 적용할 수 있을까 / 같이 보면 좋은 기술(옵션))
- **footer**: 태그, 출처 링크(보조 출처 포함).
- **sidebar (직전 회의 2차)**: 회의 질문, 같은 브랜드, 같은 flow 추천.

라이터 페르소나의 첫 발언으로 회의를 시작:

> **매거진 라이터**: 저는 글을 쓰면서 "이 슬롯에 뭘 넣어야 하지?" 한 항목당 5분 쓰고, 정작 클라이언트 회의에서 인용되는 건 1줄밖에 안 됩니다. **슬롯의 정의가 모호하거나 비슷한 게 4번 반복돼서** 결국 같은 말을 다르게 옮겨 쓰는 글이 절반.

## 회의 안건 7개

### 안건 1. 요약 섹션 골격 재정의 — 무엇이 빠졌고 무엇이 겹치나

**편집장**: SERVICE 요약은 `업데이트 / 서비스 맥락 / 변경 전 / 변경 후 / 수치·팩트` 5개. 라이터 입장에서 이 5개가 명확히 다른 정보를 담는가?

**매거진 라이터**: `업데이트`와 `변경 후`는 자주 같은 말이 됩니다. `변경 전`이 없는 신규 출시 글도 많아요. 빈 슬롯 채우려고 "기존엔 별도 진입점이 없었다" 같은 추정 문장을 쓰게 됩니다.

**클라이언트 PM**: 회의에서 제가 가장 자주 인용하는 건 **수치·팩트**입니다. "MAU 300만", "결제 단계 4→2단계". 그런데 글마다 있는 빈도가 들쭉날쭉. **누가 / 언제 / 어디서 / 얼마나** 4축이 모두 있어야 인용 가능.

**비주얼 디자이너**: 저는 `변경 전 → 변경 후` 보다 **"이 화면에서 무엇이 보이는가"가 먼저** 필요해요. 화면 캡션 같은 항목이 빠져 있습니다.

**퍼블리셔**: DEV 글은 요약 첫 두 불릿에 기술명·API·버전을 의무화했는데, SERVICE에는 그런 콘텐츠 요건이 없습니다. SERVICE에도 `핵심 변화 1줄` + `근거 데이터 1개`가 첫 두 불릿 의무 콘텐츠 요건이 있으면 좋겠습니다.

**시스템 운영자**: 골격을 바꾸면 magazine-writing-standard.md + parser의 섹션 라벨 검증도 같이 갱신해야 합니다. 가벼운 변경 아님.

**결론**:
- SERVICE 요약 5개를 **6개 명시 + 콘텐츠 요건**으로 재정의:
  1. `핵심 변화` — 1줄. 무엇이 새로 등장/사라졌는가 (의무, 첫 불릿)
  2. `근거 데이터` — 수치·기간·범위 중 최소 1개 (의무, 둘째 불릿)
  3. `서비스 맥락` — 이 브랜드가 왜 지금 이걸 했는지 (의무)
  4. `사용자 행동 변화` — 무엇이 줄거나 늘었나 (필수 → '변경 전/후' 흡수)
  5. `화면·플로우 단서` — 어디서·어떻게 보이는지 (의무, 디자이너용)
  6. `누가·언제` — 발표자·발표일·적용 범위 (옵션)
- Design 요약은 **3개**: `핵심 표현 / 적용 맥락 / 관찰 가능한 패턴` (느슨한 슬롯, 글 성격 다양해 5개 강제는 무리).
- DEV 요약은 현행 유지 (이미 콘텐츠 요건이 박혀 있음).
- writer 에이전트 프롬프트 + parser의 sub-bullet 검증 모두 갱신.

### 안건 2. 인사이트 잠금셋 4개의 의미·작성 기준 재정의

**편집장**: SERVICE는 `왜 지금 / 사용자는 무엇을 덜 / 설계 관점 / 점검 질문`. 라이터, 4개 슬롯이 명확히 다른가?

**매거진 라이터**: `왜 지금`과 `사용자는 무엇을 덜`이 자주 같은 답을 다른 시점에서 쓰는 느낌입니다. `설계 관점`도 점검 질문에서 다시 한 번 비슷한 항목이 나오고.

**클라이언트 PM**: 저는 4개 중 **`설계 관점`과 `점검 질문` 두 개**가 회의에 직접 쓰입니다. `왜 지금`과 `사용자는 무엇을 덜`은 글 도입부 맥락. 굳이 4개 슬롯일 필요가 있나?

**비주얼 디자이너**: Design 인사이트의 `어디에 적용할 수 있을까`는 자주 일반론 ("우리 서비스 홈에 적용해볼 수 있다")으로 끝납니다. 화면 단위 구체가 빠지면 의미 없음.

**퍼블리셔**: DEV의 `같이 보면 좋은 기술`은 옵션인데, 실제로는 글의 1/3 이상이 채우지 않습니다. 옵션을 의무로 바꾸거나, 채우지 않을 거면 잠금셋에서 빼야 합니다.

**매거진 라이터**: 4개 → **3개로 정리** 제안:
- SERVICE: `이 업데이트가 노리는 것` (왜+사용자 통합) / `설계 관점에서 짚을 점` / `우리 클라이언트 점검 질문`
- Design: `이 표현이 노리는 것` / `우리 화면에 옮길 때 점검할 점` / `점검 질문`
- DEV: `이 변화가 노리는 것` / `구현 시 짚을 점` / `점검 질문`

**클라이언트 PM**: 좋습니다. 4개를 3개로 줄이되, **각 슬롯에 "이 슬롯이 답해야 하는 한 질문"을 헤더 아래 회색 보조 문장으로** 박아주세요. 라이터가 슬롯 의미를 매번 떠올리지 않게.

**시스템 운영자**: 4→3 변경은 누적 글의 마이그레이션 비용이 큽니다. 기존 글은 그대로 두고, **신규 글부터 새 표준** 적용. 사이트 렌더에서 두 표준 모두 호환.

**결론**:
- 잠금셋을 4개 → **3개**로 압축. 슬롯명 카테고리별로 갱신 (위 라이터 제안 그대로).
- 각 슬롯 헤더 아래 회색 보조 문장(prompt-hint)을 마크다운 작성 표준에 추가.
- 누적 글 마이그레이션 X. 신규 글부터 적용. parser는 두 패턴 모두 인식 (3개·4개 길이 검증 보정).

### 안건 3. 클라이언트 회의 즉시 사용 가능한 요소 보강 — "인용 한 줄"과 "발표용 화면 1장"

**클라이언트 PM**: `meeting-question`은 회의에서 던질 질문 1문장이지만, 실제로 슬라이드에 띄울 **"인용 한 줄"**과 그것을 뒷받침할 **스크린샷 1장**이 따로 필요합니다. 현재는 글 본문 어딘가에 묻혀 있어 매번 다시 찾기.

**매거진 라이터**: 인용 한 줄은 안건 1의 `핵심 변화` 첫 불릿과 비슷합니다. 새로 만들지 말고 기존 첫 불릿을 그대로 인용 한 줄로 쓸 수 있게 표준화.

**비주얼 디자이너**: "발표용 화면 1장"은 갤러리의 **표지 후보** 한 장을 명시하면 됩니다. 갤러리 안에 `featured: true` 같은 메타.

**클라이언트 PM**: 슬라이드 옮기기 편하게 글 footer에 **"슬라이드용 다운로드 키트"** 같은 모듈 — 인용 1줄 + 스크린샷 + 출처 → 한 번에 복사 또는 PNG.

**편집장**: 그건 욕심이 큰 기능. 1단계는 **인용 한 줄 + featured 이미지 한 장을 article 데이터 안에 명시**하는 것까지. 다운로드는 follow-up.

**시스템 운영자**: 메타 추가:
- `핵심 인용`: 슬라이드용 1줄. 비어 있으면 `핵심 변화` 첫 불릿 자동 fallback.
- 이미지 메타에 `대표: true` 또는 `featured: true` 마킹 (없으면 첫 이미지가 자동 대표).
- 사이트 hero/footer에 `📌 슬라이드 인용` 박스로 노출 (회의 질문과 별도).

**결론**:
- `핵심 인용` 메타 라인 신설. fallback 자동.
- 갤러리 메타에 `대표` 마킹 (선택).
- 사이트 표시: 상세 footer 위 `📌 슬라이드 인용` 박스 + 카피 버튼.

### 안건 4. 출처·신뢰 박스 — 매체·저자·발행일·검증 메모를 한 곳에

**편집장**: 출처는 현재 본문 footer에 한 줄 링크. 회의에서 "이게 누가 쓴 거냐"는 질문에 매번 다시 찾아 들어가야 함.

**클라이언트 PM**: 신뢰 박스가 hero meta-row보다 본문 끝에 가까이 있는 게 자연스러워요. 다 읽고 나서 "이걸 누가 어디서 했지?"가 마지막 질문.

**매거진 라이터**: 메타에 `저자`, `매체 성격`(공식 뉴스룸/매거진/블로그/리서치)이 빠져 있습니다. `출처 유형`은 있지만 `매체명·저자명·발행일`이 따로 나뉘어야 검증 박스가 살아납니다.

**퍼블리셔**: 글로벌 출처는 `원어`와 `번역 여부`도 표시되면 좋겠어요. "이 글은 영문 원문을 직접 읽고 번역" 등.

**시스템 운영자**: 메타 추가:
- `저자` (옵션)
- `매체` (자동: 출처 도메인에서 추출하거나 명시)
- `원문 언어` (자동: 기본 ko, ja/en/zh-cn 등 명시)
- `검증 메모` (옵션, 1줄: "원문 본문 확인 + 공식 트위터 교차 확인" 등)

**비주얼 디자이너**: 박스 위치는 본문 footer 위 (`📌 슬라이드 인용` 옆 또는 아래)에 작게.

**결론**:
- 4개 메타 추가 + 본문 footer 위에 **`📚 출처 검증`** 박스. 안 채워진 필드는 라인 생략.

### 안건 5. 글 성격 라벨 — "결정용 / 맥락용 / 사례용 / 논쟁용"

**매거진 라이터**: 같은 카테고리 안에서도 글 성격이 다릅니다. "지금 도입 결정 단서가 되는 글" vs "장기 맥락 잡는 글" vs "비교 사례 모음" vs "산업 논쟁 정리".

**클라이언트 PM**: PM 입장에서 회의 직전엔 "결정용"만 우선 봅니다. "맥락용"은 이동 중 읽기.

**비주얼 디자이너**: 글 성격이 hero meta에 sourceType 배지 옆에 작게 보이면 좋겠어요. `🎯 결정용`, `🗺️ 맥락용`, `📁 사례용`, `⚔️ 논쟁용`.

**시스템 운영자**: 메타 `글 성격`: `decision | context | case | debate` 중 하나. SOURCE_TYPE_BADGES 옆에 추가 배지.

**매거진 라이터**: 자동 판정 fallback 가능 — `meeting_question`이 있으면 decision, 리서치/리포트면 context, 여러 브랜드 사례 묶음이면 case, 의견/블로그면 debate.

**결론**:
- `글 성격` 메타 신설(4종). 비어 있으면 fallback 자동 판정.
- hero meta-row에 `🎯 결정용` 등 작은 배지 (sourceType 옆).
- 사이트 카드 필터에도 활용 가능 (Explore 패널에 글 성격 칩 추가 — 별도 작업).

### 안건 6. "다음으로 볼 글" 인라인 추천 — 사이드바 보완

**편집장**: 직전 회의 2차에서 사이드바에 같은 브랜드·같은 flow 추천 카드를 넣었지만, 사이드바는 데스크탑 sticky 전용. 모바일은 본문 footer 직전에 인라인이 필요.

**클라이언트 PM**: 사이드바를 다 보고도 글 끝에서 "다음 어떤 글?"이 자연스럽게 이어지면 좋겠어요. 데스크탑에서도.

**매거진 라이터**: 추천 알고리즘은 단순해도 됨 — 같은 브랜드, 같은 flow, 같은 회차(같은 publicationDate) 3개씩 가중 점수.

**비주얼 디자이너**: 인라인 추천 카드는 가로 3개 그리드. 모바일은 세로 1열. 카드는 작은 썸네일 + h2 + 작은 메타.

**결론**:
- 글 본문 footer 위에 `## 다음으로 볼 글` 인라인 섹션. 3장.
- 추천 점수 = `같은 브랜드 +3` + `같은 flow ∩ 개수 × 1` + `같은 publicationDate +1` + `같은 changeType ∩ 개수 × 0.5`. Top 3.
- 데스크탑에서도 노출 (사이드바와 중복이지만 글 흐름 종결로서 다른 역할).

### 안건 7. 수치·인용·번역 박스 — 데이터 시각화 표준

**클라이언트 PM**: `수치·팩트`(또는 안건 1 결과 후 `근거 데이터`) 항목이 본문 평문에 묻혀 회의 슬라이드에서 다시 만들어야 합니다.

**비주얼 디자이너**: 수치는 hero/footer가 아닌 본문 안에서 **하이라이트 박스**로 빼면 임팩트가 큽니다. 예: "거래액 +47% (2026년 4월 기준, 자사 발표)" 큰 숫자 + 작은 출처.

**매거진 라이터**: 작성 시점에 `>` (blockquote)로 강조하고 있는데, 일관 패턴이 없습니다. **`> 수치: <값> · <기간> · <출처>`** 형식 표준화.

**퍼블리셔**: 인용도 영어/일본어 원문일 때 `> "Original quote" — Author, Source` 패턴. 번역은 본문에서 별도 단락. 마크다운 표준 `>`로 처리 가능.

**시스템 운영자**: parser에 새 블록 타입 `data-highlight` / `quote-translation` 신설. magazine-writing-standard에 작성 패턴 명시.

**비주얼 디자이너**: 시각화는 한 번에 욕심내지 말고 **하이라이트 박스 + 인용 박스** 두 가지만 1차 도입. 차트·표는 follow-up.

**결론**:
- 본문 작성 표준에 두 패턴 신설:
  - `> 데이터: <값> · <기간> · <출처>` → `.data-highlight` 박스
  - `> 인용: "<원문>" — <저자> · <매체>` → `.inline-quote` 박스
- parser가 두 패턴을 인식해 dedicated 블록 타입으로 변환.
- 사이트에서 큰 숫자 강조 + 작은 출처 라벨로 렌더.

### 합의 사항 3가지

1. **잠금셋은 4개 → 3개로 압축한다.** 슬롯 의미가 명확해야 라이터의 시간이 인용 한 줄을 다듬는 데 쓰인다. 신규 글부터 적용.
2. **회의에서 즉시 인용·발표 가능한 4개 요소를 항상 채운다:** `회의 질문` (직전 회의) · `핵심 인용` · `슬라이드 화면` · `근거 데이터`. 이 4개가 채워지지 않은 글은 발행 보류.
3. **출처는 본문 footer 위 검증 박스로 분리한다.** hero meta는 빠르게 스캔용, footer 박스는 "이걸 누가·어디서 했나" 마지막 검증 답.
