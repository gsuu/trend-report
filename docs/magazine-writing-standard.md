# 매거진 원고 출력 기준

이 문서는 `magazine-report.md`에 들어가는 최종 원고의 출력 형식과 세부 작성 기준만 정의합니다. 후보 선별은 `service-digest-agent-prompt.md`, `design-digest-agent-prompt.md`, `dev-digest-agent-prompt.md`를 따르고, 공통 문체와 제목·요약·태그 원칙은 `editorial-style-guide.md`를 따릅니다.

이 문서는 단일 진실(single source of truth)입니다. `templates/weekly-report.md`, `scripts/collect/prompts.mjs`의 편집 프롬프트, `AGENTS.md`의 Magazine Summary Standard는 모두 이 문서를 기준으로 동기화됩니다. 이 문서가 정한 섹션 구조 외에는 **즉흥적인 소제목을 만들지 않습니다**. 4월 28일 회차에서 발견된 `이 레퍼런스에서 먼저 볼 장면`, `검수 포인트` 같은 변형 소제목은 폐기했고, **2026-05-28 결정으로 인사이트 본문에서는 H6 소제목을 아예 쓰지 않습니다**(아래 *본문 간결화 기준* 참고).

## 본문 간결화 기준 (2026-05-28 사용자 결정)

상세 페이지 본문이 미니 에세이처럼 길어지는 것을 막기 위해, 이번 회차부터 아래를 적용합니다. **글 수(호당 건수)는 줄이지 않습니다. 글 1편의 본문만 짧고 날카롭게 합니다.** 직전 council(2026-05-27)이 의무화한 한국 응용·인용·trend-radar는 **삭제하지 않고 압축**합니다 — 정보는 100% 보존, 산문 분량만 줄입니다.

- **본문 분량**: 인사이트 본문은 읽는 글자 기준 약 700~1,200자(권장). HTML 포함 전체 본문(요약+인사이트) 3,500자 절대 상한. 절대 자수보다 아래 구조 상한으로 관리합니다.
- **소제목 폐지**: 인사이트에서 H6 소제목(`왜 지금 이 업데이트인가` 등)을 **쓰지 않습니다.** 인용 한 문장 → 단락 2~3개(빈 줄로 구분) → 응용·점검 단락으로 끝냅니다. 단락당 3문장 상한. (관련 자료 링크는 본문이 아니라 메타데이터 `관련 링크`로.)
- **요약 불릿 3~5개**: 첫 불릿=결론, 불릿당 2문장 상한, 채움 불릿 금지.
- **점검 질문 1개, 응용과 통합**: 별도 `점검 질문` 섹션을 두지 않고, 인사이트 마지막 단락에 한국 클라이언트 응용 질문 1개로 녹입니다(SERVICE/DESIGN). DEV는 점검 질문 없이 실무 적용 단락으로 끝냅니다.
- **인용/관련 자료는 본문이 아니라 출처 영역**: 카테고리별 인용(DEV 3종/SERVICE·DESIGN 2종)을 본문 산문·인사이트 끝줄에서 빼서, 메타데이터 `- 관련 링크 N: [카테고리] 제목 | URL` 줄로 옮깁니다. 렌더러가 이를 상세페이지 *출처 영역*(`출처:` 옆)에 링크로 표시합니다. 인사이트 본문에는 `관련 자료` 줄을 두지 않습니다. 인용 종수·`source-verifier` 검증 로직은 그대로.
- **JSON 스키마 무수정**: `is-bullet-summary` + `is-deep-dive` 2섹션 구조와 `block.kind` 4종은 그대로 둡니다. 바꾸는 건 블록 개수뿐(subhead 블록 미사용, paragraph 2~3개). 렌더·파서·Storybook·source-verifier 코드 변경 0.
- **경어체 통일**: 본문 모든 문장(요약 불릿·인사이트 인용 리드·단락·응용 질문)을 `~입니다/~합니다` 경어체(합쇼체)로 씁니다. `~다/~한다/~이다/~것이다` 평서체(한다체)를 섞지 않습니다. 질문은 `~까요?/~나요?`로. 요약과 인사이트의 말투가 같아야 합니다.

### 응용·점검 질문 작성 원칙

- 독자가 그 일을 **이미 한다고 단정하지 않습니다.** "운영 중인 우리는…"처럼 쓰면 안 됩니다. 독자(또는 그 클라이언트)는 그 기능을 안 쓰거나 도입 전일 수 있습니다.
- **이미 적용했으면 / 도입 전이면** 양쪽에 다 걸리는 조건형으로 씁니다.
- 한국 패션·뷰티 클라이언트명 1개 + 응용처를 그 한 문장에 박습니다.
- 예: "패션·뷰티 클라이언트에 AI 어시스턴트를 이미 붙였다면 '어시스턴트 경유 결제 완료율'을 노출/미노출 세션으로 분리해 보고 있는지, 도입 전이라면 그 측정 체계부터 설계에 넣을 수 있는지 점검할 지점이다."

## 타이틀 작성 원칙 (2026-05-26 사용자 결정)

`#### NN. 제목`의 **제목**은 **최종 기준 원문의 제목을 그대로** 가져옵니다. 매거진 측에서 임의로 헤드라인을 다시 쓰거나 번역하지 않습니다.

### 룰

1. **원문 그대로** — 영어 원문은 영어로, 한국어 원문은 한국어로. 번역·각색·요약하지 않습니다.
2. **편집 최소화** — 원문 제목이 너무 길거나 마케팅성 부제만 붙은 경우에만 메인 제목 부분을 살리고 부제는 잘라낼 수 있습니다. 핵심 단어·고유명사·따옴표·괄호 표기는 그대로 둡니다.
3. **출처 prefix는 사용하지 않음** — `[Vercel]`·`[GitHub]`·`[Smashing Magazine]` 같은 prefix를 제목 앞에 임의로 붙이지 않습니다. 출처는 `- 출처:` 메타데이터로 이미 노출됩니다.
4. **번호만 우리가 매김** — `#### NN.` 의 번호(`01`, `02`...)는 매거진 회차 내 순서이고, 그 뒤는 원문 제목 그대로.

### 좋은 예 (2026-05-26 회차)

- `#### 01. 우아한공방의 새로운 동료, 시스템 맥락을 가진 챗봇서비스 개발기(feat. RAG)`
- `#### 04. "어제처럼 자연스럽지만, 어제보다 편하게" 와일리의 하나원큐 UI·UX 리뉴얼`
- `#### 06. Four Levels Of Customer Understanding`
- `#### 08. Issue fields are now in public preview for all organizations`
- `#### 15. Nuxt MCP Toolkit now supports MCP apps`

### 나쁜 예 (피해야 할 패턴)

- 영어 원문을 한국어로 번역해서 새 제목 만들기 — `Issue fields are now in public preview...` → `Priority·Effort가 라벨이 아니라 이슈의 속성이 된다` ❌
- 매거진이 자체 캐치프레이즈로 다시 쓰기 — `우아한공방의 새로운 동료...` → `디자인시스템 문서에 챗봇이 들어왔다 — 우아한형제들이 컴포넌트를 찾는 법` ❌
- 출처 prefix 임의 부착 — `[Vercel] Chat SDK now includes...` (출처는 메타데이터에 있으므로 중복) ❌
- 정보 압축·재구성 — 원문 의도와 다른 강조점을 만드는 행위 ❌

매거진이 호기심·관점·요약으로 글의 가치를 만드는 자리는 본문의 `- 요약:` 한 줄과 `##### 매거진 인사이트` / `##### 디자인 인사이트` 섹션입니다. 타이틀은 원문에 충실합니다.

## 자체 완결 요약 원칙

요약은 그 자체로 글의 메시지가 보이게 씁니다. 독자가 원문을 열지 않아도, 메타데이터의 `요약:` 한 줄과 본문 `##### 요약` 불릿만으로 **누가 무엇을 했고, 무엇이 핵심 변화/주장인지, 왜 이 글을 봐야 하는지**가 드러나야 합니다.

자체 완결 점검 기준:

- 메타 `요약:` 1-2문장은 **주체 + 무엇을 + 어떻게/왜**가 한 문장 안에 들어갑니다. "~를 다룹니다", "~를 소개합니다", "~에 대한 글입니다" 같은 표지 문장으로 끝나면 실패입니다.
- 본문 `##### 요약`의 첫 불릿은 **글 전체의 결론 한 줄**입니다. 이후 불릿은 결론을 뒷받침하는 구체 사실(기능명, 출시 범위, 수치, 화면 변화, 작성자 주장의 근거)을 담습니다.
- 불릿은 **3~5개**, 불릿당 **2문장 상한**입니다(2026-05-28 본문 간결화 기준). 첫 불릿은 결론, 이후는 결론을 뒷받침하는 핵심 사실. 의미 없는 채움 불릿은 넣지 않습니다. 원문 밀도가 아무리 높아도 5개를 넘기지 않고, 가장 중요한 5개로 압축합니다.
- "원문은 ... 다룹니다", "기사에서는 ... 언급됩니다" 같은 메타 표현으로 불릿을 시작하지 않습니다. 원문 안의 사실로 바로 들어갑니다.
- 요약만 읽었을 때 **카테고리·출처 유형·우리 서비스에 던질 질문**까지 자연스럽게 그려져야 통과입니다.

좋은 예 (Service / 당근 AI 후기):

```
요약: 당근이 동네 가게 후기 작성 화면에 음성 입력 기반 AI 인터뷰 기능을 출시해, 사용자가 한 줄도 쓰지 않고도 후기를 남길 수 있게 했습니다. 베타 기간 후기 품질 지표가 40% 올랐다고 공개했습니다.

##### 요약
- 당근은 후기 작성 화면을 빈 입력창에서 음성 답변 기반 인터뷰로 바꿔, 첫 한 줄을 떠올리지 못해 작성을 포기하는 흐름을 끊었습니다.
- AI는 분위기·서비스 특징·이용 메뉴를 차례로 묻고, 음성 답변을 모아 후기 초안으로 정리합니다.
- 1월 베타에서 재이용률 43%, 후기 품질 지표 40% 상승이 공개됐고, 4월 전 업종으로 확대됐습니다.
```

나쁜 예 (피해야 할 패턴):

```
요약: 당근이 새로운 AI 후기 기능을 소개했습니다. 사용자에게 도움이 되는 기능입니다.
- 당근의 보도자료가 AI 후기 기능을 다룹니다.
- 기사에서는 음성 입력이 언급됩니다.
- 베타 결과도 함께 소개됐습니다.
```

이 규칙은 Service, Design, DEV 모두에 동일하게 적용합니다. DEV는 추가로 기술명·API·버전·브라우저 조건 중 하나 이상이 첫 두 불릿 안에 들어가야 합니다.

## 공통 메타데이터

모든 Service, Design, DEV 항목은 아래 메타데이터를 유지합니다.

```markdown
- 날짜: YYYY-MM-DD
- 태그: 원문 중심 태그 2-4개
- 국가: KR|GLOBAL
- 카테고리: category_key
- 직무 태그: 웹서비스기획|웹디자인|웹DEV
- 출처 유형: news|release_note|blog_opinion|reference|guide|research
- 출처: 출처명
- 출처 URL: 최종 기준 원문 URL
- 이미지: 원문 대표 이미지 URL
- 이미지 설명: 이미지 출처와 성격
- 요약: 카드와 상세 상단에 노출되는 1-2문장
```

### 카테고리 값 규칙 (필터 분류)

`- 카테고리:`에는 **소분류 키 하나만** 적습니다. **`service/`·`design/`·`dev/` 같은 대분류 접두를 붙이지 않습니다**(대분류는 `## Service`/`## Design`/`## DEV` 섹션으로 이미 정해집니다). area 접두가 붙거나 허용 목록 밖이면 사이트 필터에서 전부 `etc`로 떨어집니다. 허용 키:

| area | 허용 소분류 키 |
|---|---|
| Service | `ecommerce` `platform` `fintech` `fashion` `beauty` `ai` `insight` (없으면 `etc`) |
| Design | `ai` `global` `insight` `design_system` `tool` `update` (없으면 `etc`) |
| DEV | `html_css` `javascript` `web_accessibility` `performance` `ai` `tool` `update` `insight` (없으면 `etc`) |

- 예: `- 카테고리: ecommerce` (O) / `- 카테고리: service/ecommerce` (X — 접두 금지) / `- 카테고리: design` (X — 소분류 아님 → etc).
- Design 레퍼런스(해외 사이트·포트폴리오)는 `global`, 관점·방법론·케이스는 `insight`, AI 디자인은 `ai`로 분류합니다.
- 파서는 `service/ecommerce`처럼 접두가 붙어도 `ecommerce`로 구제하지만, 처음부터 소분류 키만 적는 것이 원칙입니다.

묶음 DEV 항목처럼 보조 원문이 있으면 `보조 출처 1`, `보조 출처 2`, `관련 링크 1` 형식으로 이어서 씁니다.

### 관련 링크(인용·관련 자료)는 메타데이터로 → 출처 영역 표시 (2026-05-28 결정)

카테고리별 인용·관련 자료는 **인사이트 본문이 아니라 메타데이터**에 둡니다. 렌더러가 이를 상세페이지 *출처 영역*(`출처:` 옆)에 링크로 표시합니다(`referenceLinks`). 형식:

```markdown
- 관련 링크 1: [카테고리] 제목 | https://...
- 관련 링크 2: [글로벌 비교] Retail Dive — Lowe's Q1 2026 성과 분석 | https://www.retaildive.com/news/...
```

- `- 요약:` 줄 **다음에** 이어서 씁니다. 번호는 글마다 1부터.
- 값은 `[카테고리] 제목 | URL` (대괄호 카테고리 유지, ` | ` 뒤 URL). `[제목](URL)` 마크다운 형식도 허용.
- **URL이 있는 출처만** 관련 링크로 둡니다. URL 없는 근거 설명(예: "제작 의도 직접 서술")은 별도 줄로 만들지 않습니다.
- 인사이트 본문에는 `관련 자료` 줄을 **두지 않습니다.**

## 인사이트 본문 구조 (2026-05-28 — 소제목 없음)

인사이트는 **소제목을 쓰지 않습니다.** 아래 순서로 흐르게 쓰고, 각 단락은 빈 줄로 구분해 읽기 쉽게 합니다. 단락은 **2~3개, 단락당 3문장 상한**.

| 영역 | 본문 섹션 | 인사이트 구성 (위 → 아래) |
|------|-----------|--------------------------|
| Service | `##### 요약` → `##### 매거진 인사이트` | 인용 1문장 → 배경 단락("왜 지금"+"무엇을 덜" 흡수) → 설계 판단 단락 → 응용·점검 단락(클라이언트 1 + 조건형 질문) |
| Design  | `##### 요약` → `##### 디자인 인사이트` | 인용 1문장 → 참고 가치 단락 → 디자인 판단 단락 → 응용·점검 단락(클라이언트 1 + 조건형 질문) |
| DEV     | `##### 요약` → `##### 매거진 인사이트` | 인용 1문장(옵션) → 구현 관점 단락(한국 4축 중 1개 한 문장 포함) → 실무 적용 단락 (점검 질문 없음) |

> 인용·관련 자료 링크는 인사이트 본문에 넣지 않고 메타데이터 `- 관련 링크 N:`으로 둬 출처 영역에 표시합니다(위 *공통 메타데이터* 참고).

폐기된 H6 소제목(`왜 지금 이 업데이트인가`, `사용자는 무엇을 덜 해도 될까`, `설계 관점`, `왜 참고할 만한가`, `어디에 적용할 수 있을까`, `디자인 관점`, `구현 관점`, `실무에 어떻게 적용할 수 있을까`, `같이 보면 좋은 기술`, `점검 질문`)은 더 이상 H6 소제목으로 쓰지 않습니다. 그 내용은 위 단락 흐름 안에 녹입니다. 기존에 금지했던 변형 소제목(`이 레퍼런스에서 먼저 볼 장면`, `적용하기 좋은 화면`, `검수 포인트`, `이번 업데이트에서 바뀐 흐름`, `실제 작업 흐름에서 볼 지점`, `도입 전 검수 포인트`, `화면에 옮길 기준`, `체크리스트로 바꿀 항목` 등)도 그대로 금지입니다.

## SERVICE 출력 형식

SERVICE 글은 서비스 화면, 정책, 전환 흐름, 운영 흐름을 설명합니다. `요약`은 원문 전체 핵심을 불릿 리스트로 정리하고, `매거진 인사이트`는 우리 서비스에 적용할 판단 기준으로 바꿉니다. 각 회차는 기사 나열로 끝내지 말고 운영 맥락(이번 주 모니터링 범위·채택한 TOP·수집했지만 제외한 것)이 함께 읽히게 정리합니다.

회차 앞머리의 운영 메모는 `## Service` 바로 아래 단락으로 씁니다. **`###` 중간 헤더(`### 이번 주 모니터링 범위`, `### 채택한 TOP 항목` 등)는 사용하지 않습니다.** 레거시 파서([scripts/notion/report_parser.py](../scripts/notion/report_parser.py))가 `### ...`를 카테고리로 해석해 그 아래 `#### 01.` 항목들의 categoryKey를 덮어쓰기 때문입니다.

권장 형식:

```markdown
## Service

이번 주 Service 모니터링 범위는 {{관심사 축}}이며 {{확인 플랫폼}}을 중점적으로 봤습니다. {{이번 주 포인트}}.

#### 01. [플랫폼] 제목
```

`수집했지만 제외한 것`은 `## 수집했지만 제외한 것`(영역 무관 공통 섹션) 또는 영역별 단락으로 둡니다. 영역 안에서는 `### 수집했지만 제외한 것`을 쓰지 않습니다.

```markdown
##### 요약

- [결론 한 줄 — 누가 무엇을 했고 핵심 변화는 무엇인지]
- [정책·수치 사실 1~2개 — GMV·전환율·승급 주기·출시 범위 등]
- [뒷받침 사실] (총 3~5불릿, 불릿당 2문장 상한, 채움 불릿 금지)

##### 매거진 인사이트

> 이 업데이트의 의미를 압축한 한 문장

배경 단락 — 왜 지금 이 변화인지, 사용자가 무엇을 덜 하게 되는지. (3문장 상한)

설계 판단 단락 — 화면 위계·정보구조·CTA·상태값·추천 근거·측정 체계 중 점검할 기준. (3문장 상한)

응용·점검 단락 — 한국 클라이언트 1개를 박은 조건형 질문 1개로 끝냅니다.
```

인용 2종(`[한국 정책]`+`[글로벌 비교]`)은 본문이 아니라 메타데이터 `- 관련 링크 1~2`로 둬 출처 영역에 표시합니다(위 *공통 메타데이터*).

SERVICE 작성 기준:

- `요약`은 3~5불릿, 첫 불릿은 결론입니다. 화면·정책·조건·전환 흐름·운영 변화 중 핵심만 압축하고, 정책·수치 사실 1~2개를 반드시 포함합니다.
- 각 SERVICE 항목은 `무엇이 바뀌었는가`, `사용자 행동이 어떻게 달라지는가`, `CTTD 클라이언트 질문으로 어떻게 바꿀 수 있는가`까지 이어져야 합니다.
- **인사이트는 소제목 없이** 인용 1문장 → 배경 단락 → 설계 판단 단락 → 응용·점검 단락으로 끝냅니다(단락당 3문장 상한). 관련 자료 줄은 본문에 두지 않습니다.
- 배경 단락에는 탐색 비용·비교 기준·전환 흐름·재방문·리뷰 신뢰·결제 조건 중 무엇이 바뀌는지와, 사용자가 탐색·비교·구매·로그인·알림 중 무엇을 덜 하게 되는지를 함께 씁니다.
- 설계 판단 단락에는 화면 위계·정보구조·CTA·상태값·피드백·추천 근거·측정 체계 중 실제로 점검할 기준을 씁니다. 수치·팩트는 원문에서 기간·출처가 확인될 때만 쓰고, 없으면 만들지 않습니다.
- 응용·점검 단락은 한국 클라이언트 1개를 박은 조건형 질문 1개로 끝냅니다(위 *응용·점검 질문 작성 원칙*). 독자가 이미 그 일을 한다고 단정하지 않습니다.
- 인용 2종(`[한국 정책]`+`[글로벌 비교]`)은 메타데이터 `- 관련 링크 N: [카테고리] 제목 | URL`로 두어 출처 영역에 표시합니다. trend-radar 시장 신호는 응용 질문에 한 줄로 흡수합니다.

## DESIGN 출력 형식

DESIGN 글은 기능 출시처럼 억지로 `변경 전/후`를 맞추지 않습니다. 실제 화면, 표현 방식, 레이아웃, 브랜드 톤, 제작 흐름을 중심으로 씁니다.

```markdown
##### 요약

- [결론 한 줄 — 무엇을, 어떻게, 왜 저장할 만한지]
- [원문에서 중요하게 다루는 사실·사례·방법·맥락] (총 3~5불릿, 불릿당 2문장 상한)

##### 디자인 인사이트

> 저장할 이유를 압축한 한 문장

참고 가치 단락 — 웹/브랜드/콘텐츠/디자인 AI 흐름 중 어디와 연결되는지. (3문장 상한)

디자인 판단 단락 — 색상·타이포·이미지·모션·컴포넌트·정보 위계·브랜드 일관성 중 검수할 기준. (3문장 상한)

응용·점검 단락 — 한국 클라이언트 1개를 박은 조건형 질문 1개로 끝냅니다.
```

인용 2종(`[케이스 출처]`+`[결정 근거]`)은 본문이 아니라 메타데이터 `- 관련 링크 1~2`로 둬 출처 영역에 표시합니다(위 *공통 메타데이터*).

DESIGN 작성 기준:

- 본문 `요약`은 3~5불릿으로 원문 내용을 압축합니다. 원문에 없는 적용처나 해석을 넣지 않습니다.
- **인사이트는 소제목 없이** 인용 1문장 → 참고 가치 단락 → 디자인 판단 단락 → 응용·점검 단락으로 끝냅니다(단락당 3문장 상한). 관련 자료 줄은 본문에 두지 않습니다.
- 참고 가치 단락에는 웹디자인·브랜드 디자인·콘텐츠 디자인·디자인 AI 흐름 중 어디와 연결되는지 씁니다.
- 디자인 판단 단락에는 색상·타이포그래피·이미지/영상 연출·모션·컴포넌트·정보 위계·브랜드 일관성 중 검수할 기준을 씁니다. 적용 범위(랜딩·상세·캠페인·룩북·에디토리얼·디자인 시스템·AI 제작 흐름)는 응용·점검 단락에서 다룹니다.
- 응용·점검 단락은 다음 시안이나 운영 페이지에 바로 대입할 조건형 질문 1개로 끝냅니다(한국 클라이언트 1개 포함, 독자가 이미 한다고 단정 금지).
- 인용 2종(`[케이스 출처]`+`[결정 근거]`)은 메타데이터 `- 관련 링크 N: [카테고리] 제목 | URL`로 두어 출처 영역에 표시합니다.

## DEV 출력 형식

DEV 글은 구현, 접근성, 브라우저 QA, 컴포넌트, 배포 검증에서 무엇을 확인해야 하는지 보여줘야 합니다.

```markdown
##### 요약

- [결론 한 줄 — 무엇이 바뀌었고 무엇을 확인해야 하는지]
- [기능명·API/속성·브라우저 조건·접근성 조건 중 하나 이상 — 첫 2불릿 안에]
- [제한점·검증 방법] (총 3~5불릿, 불릿당 2문장 상한)

##### 매거진 인사이트

> (옵션) 핵심을 압축한 한 문장

구현 관점 단락 — 영향받는 컴포넌트·브라우저·접근성 QA·디자인 시스템·배포 검증. 한국 환경 4축(iOS Safari·한글·모바일·접근성) 중 1개를 한 문장으로 포함. (3문장 상한)

실무 적용 단락 — 다음 분기 QA 체크리스트·적용 조건·롤백 기준으로 바꿔 씁니다. (3문장 상한)
```

인용 3종(`[합성 데모]`/`[공식 사양]`/`[프로덕션 사례]`)은 본문이 아니라 메타데이터 `- 관련 링크 1~3`으로 둬 출처 영역에 표시합니다(위 *공통 메타데이터*).

DEV 작성 기준:

- 용어를 별도 섹션으로 풀이하지 않습니다. 일반 독자가 바로 이해하기 어려운 제품명·도구명·약어가 있을 때는 `요약` 첫 등장 위치에서 괄호로 풀어 설명합니다(예: `Radix UI(접근성 중심의 headless UI primitive 라이브러리)`).
- `요약`은 3~5불릿, 첫 불릿은 결론입니다. 원문에서 확인한 구체 사실을 포함해야 하고, "~를 소개합니다", "유용합니다" 같은 빈 문장은 실패입니다.
- 릴리즈/문서라면 기능명, 도구명, API/속성, 브라우저·접근성·성능 조건, 수치, 제한점, 검증 방법 중 하나 이상을 넣습니다.
- 블로그/오피니언 글이라면 작성자의 핵심 주장, 근거 사례, 비교 대상, 실무 판단 기준을 분리합니다.
- **인사이트는 소제목 없이** (옵션) 인용 1문장 → 구현 관점 단락 → 실무 적용 단락으로 끝냅니다(단락당 3문장 상한). DEV는 **점검 질문을 두지 않습니다.** 관련 자료 줄은 본문에 두지 않습니다.
- 구현 관점 단락에는 어떤 컴포넌트·브라우저·접근성 QA·디자인 시스템·배포 검증에 영향이 있는지와, 한국 환경 4축(iOS Safari·한글·모바일·접근성) 중 1개를 한 문장으로 넣습니다(별도 단락으로 빼지 않음).
- 인용 3종(`[합성 데모]`/`[공식 사양]`/`[프로덕션 사례]`)은 메타데이터 `- 관련 링크 1~3` **3줄 모두 필수**로 두어 출처 영역에 표시합니다.
- code 스타일은 실제 코드성 표현에만 씁니다. 기능명, 제품명, 한국어 UI 문구, 강조 문장에는 쓰지 않습니다.

## 카테고리별 보강 기준

상세페이지는 같은 형식 안에서도 카테고리별로 읽을거리가 달라야 합니다. 아래 기준 중 해당 이슈에 가장 맞는 1-2개만 반영합니다.

### Service / fashion

- 브랜드관, 룩북, 카테고리 홈, 오프라인 매장, 찜/재입고처럼 `발견 → 저장 → 재방문` 흐름이 어떻게 이어지는지 봅니다.
- 할인보다 큐레이션 구조, 스타일 문맥, 브랜드 스토리, 저장 이후 알림/재방문 장치를 우선 설명합니다.
- 오프라인 이슈는 매장 규모보다 온라인 행동이 매장 이후 어떻게 회수되는지를 봅니다.

### Service / platform

- 로컬, 커뮤니티, 콘텐츠, 리서치, 검색/추천처럼 여러 참여자를 연결하는 구조를 봅니다.
- 리뷰, 후기, 프로필, 추천, 알림, 온보딩, 신고/검수 같은 신뢰 장치가 화면에서 어떻게 설명되는지 봅니다.

### Service / fintech

- 결제, 송금, 정산, 포인트, 캐시, 회비, 금융 조건처럼 돈의 흐름을 사용자가 오해하지 않게 만드는 UX를 봅니다.
- 혜택 총액보다 적용 조건, 보상 시점, 실패/취소/환불 상태, 수수료나 회비 회수 판단을 설명합니다.

### Service / ecommerce

- 멤버십, 무료배송, 페이백, 쿠폰, 리뷰, AI 검색처럼 `구매 전 불안`과 `결제 직전 계산 부담`을 낮추는 장치를 봅니다.
- AI 추천/검색은 답변 생성보다 비교 기준, 추천 근거, 상품 카드 연결, 필터 재조정 흐름을 우선합니다.

### Service / department_store

- VIP, 선물, 픽업, 예약, 오프라인 재고, 행사 동선처럼 온라인과 매장 경험이 어떻게 분담되는지 봅니다.
- 프리미엄 경험은 예약 확정, 혜택 적용, 매장 방문 전후 알림 같은 상태값이 명확한지 설명합니다.

### Service / beauty

- 피부 진단, 성분 비교, 리뷰, 랭킹, 듀프, 개인화 추천처럼 `신뢰 근거`가 화면에서 어떻게 설명되는지 봅니다.
- 글로벌/오프라인 확장은 상품 수출보다 현지 사용자가 처음 신뢰를 얻는 접점을 봅니다.

### Service / book_content

- 이어보기, 책갈피, 로그인 복구, 구독/소장/대여 결제, 추천 홈처럼 `중단 후 복귀`와 `콘텐츠 소유감`을 봅니다.

### Design

- 도구 소개보다 제작 순서, 승인 흐름, 브랜드 가이드 적용, 디자인 시스템과의 충돌, 최종 편집 가능성을 봅니다.
- AI 디자인 이슈는 결과물이 예쁜지보다 누가 검수하고, 어떤 원본/권리/컴포넌트 규칙을 기준으로 통과시키는지 설명합니다.

### DEV

- 릴리즈 소개보다 적용 조건, 영향을 받는 화면, 브라우저/런타임 호환성, 테스트와 롤백 기준을 봅니다.
- 브라우저 업데이트는 새 API 나열보다 다음 분기 컴포넌트 QA 체크리스트로 바꿉니다.

## 유익한 정보 구성

각 상세페이지는 아래 4가지 정보가 구분되어야 합니다.

- 확인된 사실: 원문에서 확인한 날짜, 기능, 범위, 수치, 제한
- 해석: 이 변화가 왜 지금 나왔고 어떤 흐름과 연결되는지
- 적용 기준: 우리 서비스에서 어떤 화면, 정책, 컴포넌트, 운영 규칙을 점검해야 하는지
- 주의점: 원문에서 확인되지 않은 수치, 과장하면 안 되는 효과, 도입 전 필요한 조건

본문에 별도 표를 만들 필요는 없지만, 문단 안에서 이 네 가지가 섞여 흐려지지 않게 씁니다.

## 설계 판단 단락 작성 지침

인사이트의 **설계 판단 단락**(Design은 디자인 판단 단락, DEV는 구현 관점 단락)은 인사이트의 핵심입니다. 소제목 없이 한 단락(3문장 상한)으로 쓰되, "이 기능이 생겼다"가 아니라 "이 변화에서 어떤 설계 판단을 읽어야 하는가"를 보여줘야 합니다.

반드시 포함할 관점:

- 화면 위계: 사용자가 가장 먼저 봐야 할 정보, CTA, 보조 정보의 우선순위
- 정보구조: 홈, 상세, 목록, 검색, 찜, 멤버십, 로그인 이후 화면이 어떤 순서로 이어지는지
- 행동 흐름: 탐색, 비교, 저장, 알림, 결제, 재방문 중 어느 행동을 줄이거나 강화하는지
- 판단 근거: 추천, 혜택, AI, 멤버십, 콘텐츠 카드가 사용자를 설득하는 근거를 충분히 보여주는지
- 상태와 피드백: 적용됨, 저장됨, 보상 받음, 혜택 가능, 이어보기 가능 같은 상태가 화면에서 명확한지

쓰지 말아야 할 문장:

- “사용자 경험을 개선했다”처럼 결과만 말하는 문장
- “중요하다”, “좋은 사례다”처럼 설계 근거가 없는 평가
- 기사 본문, 보도자료, 앱 릴리즈 노트를 다시 요약하는 문장
- 매출, 성장, 성과를 UX 효과처럼 단정하는 문장

## JSON 섹션 스키마 (magazine.json 출력)

마크다운 `magazine-report.md`는 `scripts/notion/export_magazine_json.py`(레거시) 또는 `scripts/collect/store.mjs`(신규)에서 아래 JSON 섹션 구조로 변환되어 `public/data/magazine.json`에 저장됩니다. AI 편집 단계에서 직접 JSON을 출력할 때도 같은 스키마를 따릅니다.

### Service / Design 공통

```json
{
  "sections": [
    {
      "title": "요약",
      "className": "article-section is-bullet-summary",
      "prose": false,
      "blocks": [
        { "kind": "list", "html": "첫 불릿 = 글 전체 결론 한 줄" },
        { "kind": "list", "html": "정책·수치 사실 1~2개 (기능명·범위·수치·화면 변화·작성자 주장 근거 등)" },
        { "kind": "list", "html": "뒷받침 사실 — 총 3~5불릿, 불릿당 2문장 상한, 채움 불릿 금지" }
      ]
    },
    {
      "title": "매거진 인사이트",
      "className": "article-section is-deep-dive",
      "prose": true,
      "blocks": [
        { "kind": "quote", "html": "이 업데이트의 의미를 압축한 한 문장" },
        { "kind": "paragraph", "html": "배경 단락 — 왜 지금 + 사용자가 무엇을 덜 (3문장 상한)" },
        { "kind": "paragraph", "html": "설계 판단 단락 (3문장 상한)" },
        { "kind": "paragraph", "html": "응용·점검 단락 — 한국 클라이언트 1개 + 조건형 질문 1개 (인사이트의 마지막 블록)" }
      ]
    }
  ]
}
```

소제목(`subhead`) 블록은 더 이상 쓰지 않습니다. 인사이트는 `quote` 1개 + `paragraph` 2~3개(배경·판단·응용)로만 구성하고, **관련 자료 링크 블록을 넣지 않습니다.** 인용·관련 자료는 메타데이터 `관련 링크 N:`에서 `referenceLinks`로 변환돼 상세페이지 *출처 영역*에 표시됩니다(`{ "label": "관련 링크", "title": "[카테고리] 제목", "url": "https://..." }`). Design은 `title`을 `"디자인 인사이트"`로 두고 블록 구성 동일(quote + 참고 가치·디자인 판단·응용 paragraph). DEV는 점검 질문 단락 없이 `구현 관점 → 실무 적용` paragraph로 두고, 첫 `quote`는 옵션입니다.

용어 풀이가 필요하면 `요약` 불릿 안에서 괄호로 짧게 처리합니다(예: `Radix UI(접근성 중심 headless UI primitive)`). 별도 `용어 설명` 섹션은 두지 않습니다.

### 클래스명 규약

| className | Vue 렌더 | 용도 |
|-----------|----------|------|
| `article-section is-bullet-summary` | `<ul class="bullet-summary-list">` | `요약` 섹션 (불릿 리스트, 자체 완결 요약 원칙 적용) |
| `article-section is-deep-dive` (`prose: true`) | `<div class="section-prose">` + 블록별 렌더 | 인사이트 섹션 (quote 1 + paragraph 2~4; subhead·list 미사용) |
| `article-section is-cluster-member` | 클러스터 멤버 카드 | 같은 주제 묶음 카드 (자동 생성) |
| `article-section is-related-service` | 관련 서비스 정보 | `related-service.mjs`가 자동 추가 |

### 블록 종류 (`block.kind`)

- `list` — 불릿 리스트 항목. **`is-bullet-summary`(요약) 안에서만** 씁니다(3~5개). 인사이트(`is-deep-dive`)에서는 쓰지 않습니다 — 점검 질문도 `paragraph`로 녹입니다.
- `quote` — 인사이트 리드 문장. 인사이트 섹션의 첫 블록으로만 사용합니다(DEV는 옵션).
- `subhead` — 인사이트 H6 소제목. **2026-05-28 결정으로 더 이상 사용하지 않습니다.** 스키마 호환을 위해 kind 자체는 남겨두지만 신규 글에는 넣지 않습니다.
- `paragraph` — 일반 문단. 인사이트 본문(배경·판단·응용)은 모두 `paragraph`로 씁니다. 관련 자료 링크는 인사이트에 넣지 않고 메타데이터 `관련 링크`(→ `referenceLinks`, 출처 영역)로 둡니다.

이 4종 외 다른 `kind`는 추가하지 않습니다. 스키마(섹션·className·block.kind 4종)는 그대로 두고, 바꾸는 것은 블록 개수·사용 빈도뿐입니다 — 렌더·파서·`source-verifier` 코드 변경은 없습니다.
