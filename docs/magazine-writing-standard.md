# 매거진 원고 출력 기준

이 문서는 `magazine-report.md`에 들어가는 최종 원고의 출력 형식과 세부 작성 기준만 정의합니다. 후보 선별은 `service-digest-agent-prompt.md`, `design-digest-agent-prompt.md`, `dev-digest-agent-prompt.md`를 따르고, 공통 문체와 제목·요약·태그 원칙은 `editorial-style-guide.md`를 따릅니다.

이 문서는 단일 진실(single source of truth)입니다. `templates/weekly-report.md`, `scripts/collect/prompts.mjs`의 편집 프롬프트, `AGENTS.md`의 Magazine Summary Standard는 모두 이 문서를 기준으로 동기화됩니다. 이 문서가 정한 섹션 구조와 소제목 외에는 **즉흥적인 소제목을 만들지 않습니다**. 4월 28일 회차에서 발견된 `이 레퍼런스에서 먼저 볼 장면`, `검수 포인트` 같은 변형 소제목은 이번 회차부터 폐기합니다.

## 자체 완결 요약 원칙

요약은 그 자체로 글의 메시지가 보이게 씁니다. 독자가 원문을 열지 않아도, 메타데이터의 `요약:` 한 줄과 본문 `##### 요약` 불릿만으로 **누가 무엇을 했고, 무엇이 핵심 변화/주장인지, 왜 이 글을 봐야 하는지**가 드러나야 합니다.

자체 완결 점검 기준:

- 메타 `요약:` 1-2문장은 **주체 + 무엇을 + 어떻게/왜**가 한 문장 안에 들어갑니다. "~를 다룹니다", "~를 소개합니다", "~에 대한 글입니다" 같은 표지 문장으로 끝나면 실패입니다.
- 본문 `##### 요약`의 첫 불릿은 **글 전체의 결론 한 줄**입니다. 이후 불릿은 결론을 뒷받침하는 구체 사실(기능명, 출시 범위, 수치, 화면 변화, 작성자 주장의 근거)을 담습니다.
- 불릿 개수는 제한하지 않습니다. 원문을 대표하는 의미 있는 포인트를 필요한 만큼 담되, 의미 없는 채움 불릿은 넣지 않습니다. 원문 밀도가 높으면 5개, 7개도 됩니다.
- "원문은 ... 다룹니다", "기사에서는 ... 언급됩니다" 같은 메타 표현으로 불릿을 시작하지 않습니다. 원문 안의 사실로 바로 들어갑니다.
- 요약만 읽었을 때 **카테고리·출처 유형·우리 서비스에 던질 질문**까지 자연스럽게 그려져야 통과입니다.

좋은 예 (Service / 당근 AI 후기):

```
요약: 당근이 동네 가게 후기 작성 화면에 음성 입력 기반 AI 인터뷰 기능을 출시해, 사용자가 한 줄도 쓰지 않고도 후기를 남길 수 있게 했습니다. 베타 기간 후기 품질 지표가 40% 올랐다고 공개했습니다.

##### 요약
- 당근은 후기 작성 화면을 빈 입력창에서 음성 답변 기반 인터뷰로 바꿔, 첫 한 줄을 떠올리지 못해 작성을 포기하는 흐름을 끊었습니다.
- AI는 분위기·서비스 특징·이용 메뉴를 차례로 묻고, 음성 답변을 모아 후기 초안으로 정리합니다.
- 1월 베타에서 재이용률 43%, 후기 품질 지표 40% 상승이 공개됐고, 4월 전 업종으로 확대됐습니다.
```

나쁜 예 (피해야 할 패턴):

```
요약: 당근이 새로운 AI 후기 기능을 소개했습니다. 사용자에게 도움이 되는 기능입니다.
- 당근의 보도자료가 AI 후기 기능을 다룹니다.
- 기사에서는 음성 입력이 언급됩니다.
- 베타 결과도 함께 소개됐습니다.
```

이 규칙은 Service, Design, DEV 모두에 동일하게 적용합니다. DEV는 추가로 기술명·API·버전·브라우저 조건 중 하나 이상이 첫 두 불릿 안에 들어가야 합니다.

## 공통 메타데이터

모든 Service, Design, DEV 항목은 아래 메타데이터를 유지합니다.

```markdown
- 날짜: YYYY-MM-DD
- 태그: 원문 중심 태그 2-4개
- 국가: KR|GLOBAL
- 카테고리: category_key
- 직무 태그: 웹서비스기획|웹디자인|웹DEV
- 출처 유형: news|release_note|blog_opinion|reference|guide|research
- 출처: 출처명
- 출처 URL: 최종 기준 원문 URL
- 이미지: 원문 대표 이미지 URL
- 이미지 설명: 이미지 출처와 성격
- 이미지 2 / 이미지 3 …: (선택) 같은 글의 추가 스크린샷. 함께 `이미지 2 설명:` / `이미지 3 설명:`을 둔다. 2장 이상이면 사이트에서 가로 스크롤 갤러리로 노출됨
- 요약: 카드와 상세 상단에 노출되는 1-2문장
- 회의 질문: **우리 에이전시가 클라이언트 미팅에서 제안 직후 던질** 1문장 (SERVICE 의무, Design/DEV 선택)
- 핵심 인용: **클라이언트 제안 슬라이드에 그대로 옮길** 1문장 (SERVICE 권장; 비어 있으면 본문 '핵심 변화' 첫 불릿 또는 메타 요약 자동 fallback)
- CodePen / Stackblitz / Codesandbox / Storybook / GitHub / 데모 / 코드 스니펫 / 환경설정: 코드 산출물 (DEV-퍼블리셔 의무 1개 이상, 나머지 선택)
- 흐름: checkout/주문|온보딩|검색|비교/추천|리뷰|결제|멤버십|알림 등 글이 속한 화면/플로우 1~3개 (자동 추출 fallback 있음)
- 변화 유형: 정책|화면|플로우|기능|제거|리브랜딩|릴리즈|리포트 중 1~2개 (자동 추출 fallback 있음)
- 브랜드: 정규화된 브랜드명 1개 (예: '오늘의집', '무신사', '11ty', '오픈서베이' — 자동 추출 fallback 있음)
- 글 성격: decision|context|case|debate 중 하나 (자동 fallback: meeting_question 있으면 decision, research면 context, 여러 브랜드 비교면 case, blog_opinion이면 debate)
- 저자: 원문 저자명 (선택, 매거진 검증 박스에 노출)
- 매체: 원문 매체명 정규화 (선택; 비어 있으면 출처 라인 fallback)
- 원문 언어: ko|ja|en|zh-cn 중 하나 (선택; 비어 있으면 locale에서 자동)
- 검증 메모: 어떻게 검증했는지 1줄 — **클라이언트 임원의 깐깐한 출처 질문에 즉답하기 위함**. 예: "원문 본문 직접 확인 + 공식 트위터 교차 확인" (선택, 매거진 검증 박스에 노출)
- 클라이언트 적합: 표준 키워드 셋 중 2~4개 — fashion_commerce, beauty_commerce, food_d2c, lifestyle_commerce, fintech, content_platform, marketplace, o2o, b2b_saas, travel, healthcare, edu (선택; 비어 있으면 category/brand에서 자동 fallback)
```

묶음 DEV 항목처럼 보조 원문이 있으면 `보조 출처 1`, `보조 출처 2`, `관련 링크 1` 형식으로 이어서 씁니다.

### `회의 질문` 메타 규칙 — 에이전시 시점 v2

- **SERVICE 글에는 반드시 작성합니다.** 본문 `점검 질문` 섹션의 핵심 1문장을 그대로 옮기거나 더 압축해 한 문장으로 씁니다.
- Design / DEV 글은 선택입니다. 작성하면 사이트 상세 페이지 상단에 `💬 클라이언트에게 묻기` 박스로 노출됩니다.
- 메타 라인이 비어 있어도 `점검 질문` 섹션 첫 문장이 자동으로 fallback 추출되므로 점검 질문 섹션 자체는 SERVICE·Design 모두 의무입니다. 다만 자동 추출은 보강용이고, 표준 작성 흐름은 메타 라인 명시입니다.
- 작성 기준 (**에이전시 v2**): "**우리 에이전시(CTTD)가 클라이언트 의사결정자에게 제안 직후 던질 한 문장 질문.**" "우리 서비스" 화법 금지, 항상 "**클라이언트사의 ~화면·정책·지표·기획**"으로 씁니다. 좋은 예: "이번 분기 클라이언트사 결제 화면에서 멤버십 할인이 적용된 최종가 위에 회비 회수까지 며칠 남았는지 보이는 표시가 있나요?"

### 코드 산출물 메타 규칙 (DEV-퍼블리셔)

- DEV 카테고리(퍼블리셔 독자) 글은 **`CodePen` / `Stackblitz` / `Codesandbox` / `Storybook` / `GitHub` / `데모` / `코드 스니펫` / `환경설정` 메타 중 1개 이상을 의무로 작성**합니다.
- vite·11ty·Astro·Tailwind·PostCSS 환경설정을 다루는 글은 `환경설정: <filename> https://...` 형식으로 별도 메타 라인을 둡니다. 사이트에서 노란색 강조 배지로 노출됩니다.
- 값 형식: `라벨: [표기명](URL)` 또는 `라벨: 표기명 https://...` 또는 `라벨: URL`. URL 없이 코드 스니펫명만 적으면 정적 배지로 표시됩니다.
- Service/Design 글은 선택입니다. 작성하면 같은 위치에 배지로 노출됩니다.

### 본문 안 데이터·인용 박스 패턴

본문 안에서 강조하고 싶은 수치나 원문 인용은 다음 2개 패턴을 사용합니다. 둘 다 markdown `>` blockquote에 라벨 prefix를 붙이는 형식.

```markdown
> 데이터: 거래액 +47% · 2026년 4월 기준 · 자사 발표
> 인용: "We've found that personalization works only when…" — Jane Doe · NN/g
```

사이트 표시:
- `> 데이터: …` → 노란색 큰 숫자 박스 (📊 데이터 라벨 + 본문)
- `> 인용: …` → 회색 보더 인용 박스 (❝ 인용 라벨 + 이탤릭 본문)

기존 `> ...` (라벨 없음)은 잠금 소제목 보조 문장(prompt-hint) 또는 인사이트 lead로 처리됩니다. 데이터·인용 박스를 쓸 때는 반드시 `데이터:` 또는 `인용:` 라벨을 prefix로 둡니다.

## v3 본문 형식 (신규 글 기준, 사실 기반 큐레이션)

**2026-05-24 이후 신규 글은 모두 이 형식으로 작성**합니다. 직전 4번째 회의의 잠금셋 v2(요약 6슬롯 + 인사이트 3슬롯)는 신규 글에서 폐기되고, 누적 글만 호환을 위해 사이트가 그대로 렌더합니다. 자세한 합의 이력: [v3-direction](article-content-redesign-v3-direction-2026-05.md) · [v3.1-curatorial](article-content-redesign-v3.1-curatorial-2026-05.md) · [v4-facts-only](article-content-redesign-v4-facts-only-2026-05.md).

### 글 전체 구조

```markdown
#### 01. [플랫폼] 제목

(메타 라인 블록: 날짜·태그·국가·카테고리·직무 태그·출처·이미지·요약·
 큐레이션 사유·이 글에서 만나는 것·외부 참고·flow·brandNormalized 등)

##### 매거진

(씬 → 흐름 → 함의 3단락, 라벨 없는 흐르는 글, 600-900자.
 본문 안에 `> 데이터:` / `> 인용:` 박스 자유롭게 활용)

##### 심화: <제목>   ← 선택. 0~3개 H3 단위로 자유.

(심화 단락. 라이터 의지로 디테일 보존.)
```

- `##### 매거진` 섹션이 있으면 parser가 글을 **v3 형식으로 인식**하고, payload에 `articleVersion: "v3"` 마크합니다.
- `##### 매거진`이 없으면 누적 글(v2 잠금셋 형식)로 인식해 기존 렌더.
- 큐레이션 인덱스 3블록은 본문에 직접 쓰지 않고 메타에서 자동 합성됩니다.

### 매거진 블록 작성 가이드 (`##### 매거진` 600-900자, 3단락)

| 단락 | 정의 | 작성 기준 |
|---|---|---|
| **씬 (Scene)** | 사건의 도입 | 출처 원문에 실제 있는 인용·날짜·인물·장소·화면 캡션. 라이터가 상상한 장면 금지. 1-2 문장. |
| **흐름 (Flow)** | 사실 병치 | **같은 시기·같은 분야·같은 패턴의 다른 사실 1-2개를 나란히 놓는다.** 작가 입장 표명 X. 사실을 나란히 놓는 것만으로 독자가 흐름을 읽게 한다. 2-4 문장. |
| **함의 (Implication)** | 발화자 인용 또는 명시된 다음 단계 | **출처에 나온 발화자(공식 발표·임원 인터뷰·연구자 코멘트) 한 명의 말을 인용**하거나, 그 사건의 **명시된 다음 단계(공식 로드맵·다음 분기 발표 예고)** 를 사실로 적는 것까지. 라이터의 함의 설명 금지. 1-2 문장. |

세 단락 사이에 라벨(`###### 씬` 같은 H6)을 두지 않습니다. 독자에게는 흐르는 한 글로 읽히고, 라이터·검수자만 가이드로 인식합니다.

라이터의 행위는 슬롯 채우기가 아니라 **"사실의 큐레이션·병치·인용 배치"** 입니다.

### 사실 기반 원칙 (절대 규칙)

**본문 모든 문장은 다음 3종 사실 중 하나에 묶여야 합니다.**

| 사실 종류 | 예시 | 형식 |
|---|---|---|
| **공개 사실** | 공식 발표·릴리즈 노트·임원 인터뷰·공식 통계·뉴스 보도 | "토스는 2026년 5월 20일 자사 공식 블로그 'toss.tech'에서 ~을 공개했다." |
| **관찰 가능한 사실** | 우리가 직접 화면을 캡처해 확인한 UI·플로우·정책 | "오늘의집 '로컬의 선택' 진입 화면에는 144종 상품이 3개 테마 탭으로 정리되어 있다 (2026년 5월 22일 캡처)." |
| **인용된 사실** | 다른 매체·연구·전문가가 발화한 진술 | "NN/g 리포트(2026.5.8)에 따르면 Qwen AI 에이전트는 ~." |

**금지 표현 (magazine-reviewer가 자동 검출, 검출 시 라이터에게 수정 메모)**:

| 분류 | 패턴 |
|---|---|
| 강한 추측 (11종) | `~로 보인다 / ~할 것 같다 / ~할 듯하다 / ~로 풀이된다 / ~로 해석된다 / ~로 분석된다 / ~로 평가된다 / ~로 받아들여진다 / 시사하는 바가 크다 / 시사점을 준다 / 의미가 크다` |
| 단정 부사 (5종) | `사실상 / 분명히 / 누구나 알다시피 / 업계 전반에서 / 모두가` |
| 전망 추측 (8종) | `~가 될 전망(이다) / ~할 것으로 예상(된다) / ~할 가능성이 높다 / 앞으로 ~할 것이다 / 다음 ~엔 ~할 / ~가 될 것으로 보인다 / 아마 / 추측 / 예측` |
| 평가 형용사 (인용 없이 라이터가 직접 쓰면 경고) | `혁신적(인) / 획기적(인) / 독보적(인) / 압도적(인) / 놀라운 / 대단한 / 굉장한 / 최고의 / 최초의(공식 발표 인용 없이)` |

**예외 — 추측은 인용 박스로 변환 가능**:

원문 발화자(분석가·작가·연구자)가 한 추측은 인용 박스로 분리해 사실로 변환할 수 있습니다.

```markdown
❌ 본문: 이 변화는 결제 시장에 큰 영향을 줄 것으로 보인다.
✅ 본문: > 인용: "이 변화는 결제 시장에 큰 영향을 줄 것으로 본다." — 김OO 핀테크 분석가, ChosunBiz 2026.5.18
```

blog_opinion·research·미래 전망 글 모두 같은 원칙 적용. 예외 없음.

### 큐레이션 인덱스 3블록 (메타에서 자동 합성)

본문 매거진 블록 직후, 사이트는 다음 3블록을 카드 형태로 자동 렌더합니다. 라이터는 메타 라인만 채우면 됩니다.

| 블록 | 내용 | 메타·자동 소스 |
|---|---|---|
| 📝 **에디터의 큐레이션 노트** | "왜 이 글을 이번 호에 골랐는지" 1-3문장. 작가/편집자의 사실 기반 큐레이션 사유. | `큐레이션 사유` 메타 (**의무**) |
| 📖 **이 글에서 만나는 것** | 본문에서 다루는 사람·장면·숫자·도구·브랜드 3-5개. 콘텐츠 가이드. 액션 아님. | `이 글에서 만나는 것` 메타 (선택, 비면 본문에서 자동 추출) |
| 📚 **같이 살펴보면 좋은 글** | 우리 누적 글 중 관련 글 (같은 브랜드·flow·회차 가중) + 외부 참고 글 3-6개 | `flow` / `brandNormalized` 자동 매칭 + `외부 참고` 메타 (선택, URL 1-3개) |

**큐레이션 노트 톤**: "이 글이 다루는 ~한 점이 이번 호 SERVICE의 ~ 관심사와 닿는다" 같은 사실 기반 큐레이션 사유. 단정 화법(`사실상·분명히·누구나`)이나 강한 추측 표현 금지.

좋은 큐레이션 노트 예: "오늘의집의 로컬 큐레이션과 컬리의 신선식품 협업은 같은 주에 발표됐다. 두 사례 모두 자체 카테고리 위에 외부 브랜드 협업을 얹는 패턴이라 이번 호 SERVICE에서 함께 다룬다."

### 심화 섹션 (선택)

본문 매거진 블록과 큐레이션 인덱스 이후, 라이터 의지로 디테일을 보존하고 싶으면 `##### 심화: <제목>` 형식으로 H3 단위 1-3개 추가합니다. 형식 자유. 사실 기반 원칙은 동일 적용. 슬롯 없음.

### 인용·데이터 박스 사용 권장

본문 매거진 블록 600-900자 안에 **데이터 박스 1개 이상 + 인용 박스 1개 이상**을 권장합니다(의무는 아님). 사실 기반 본문의 핵심 도구. magazine-reviewer는 인용·데이터 박스 0개 글에 "사실 인용 부족" 경고를 출력합니다.

```markdown

> 인용: "We've found that personalization works only when…" — Jane Doe · NN/g · 2026-05-08
```

## 잠금 소제목 셋 (Locked sub-headings) — v2, 누적 글 호환용

각 영역의 인사이트 본문 소제목은 아래 **3개**로 고정합니다(2026-05-24 회의 결정으로 4→3 압축). 다른 표현으로 대체하거나 영역 사이에서 섞지 않습니다. 직전 4개 잠금셋(`왜 지금 / 사용자는 무엇을 덜 해도 될까 / 설계 관점 / 점검 질문`)으로 작성된 누적 글은 그대로 두고 **신규 글부터 새 표준** 적용합니다.

| 영역 | 본문 섹션 | 인사이트 소제목 (H6, 3개 고정, **에이전시 시점 v2**) |
|------|-----------|--------------------------------|
| Service | `##### 요약` → `##### 매거진 인사이트` | 이 변화가 클라이언트 사업에 닿는 지점 / 우리가 제안할 수 있는 액션 가설 / 우리 클라이언트 점검 질문 |
| Design  | `##### 요약` → `##### 디자인 인사이트` | 이 표현이 어울리는 클라이언트 톤 / 우리 시안에 옮길 때 가져올·다듬을 요소 / 점검 질문 |
| DEV     | `##### 요약` → `##### 매거진 인사이트` | 이 변화가 우리 프로젝트에서 줄이는 작업 / 클라이언트 프로젝트에 적용할 때 짚을 점 / 점검 질문 |

각 소제목 바로 아래 첫 단락 시작 전에 **회색 보조 한 줄(prompt-hint)** 을 둡니다. 이 한 줄은 "이 슬롯이 답해야 하는 한 질문"이며, 본문이 아니라 라이터·검수자용 보조 텍스트입니다. 사이트 표시는 회색 작은 글씨로 렌더되며 글의 길이에는 포함되지 않습니다.

```markdown
###### 이 변화가 클라이언트 사업에 닿는 지점
> 어느 종류의 클라이언트(패션 커머스·식품 D2C·핀테크 등)에서 어떤 사업 결정이 흔들리는가?

(본문 단락…)
```

소제목 추가 금지 항목: `이 레퍼런스에서 먼저 볼 장면`, `적용하기 좋은 화면`, `검수 포인트`, `이번 업데이트에서 바뀐 흐름`, `실제 작업 흐름에서 볼 지점`, `도입 전 검수 포인트`, `가이드가 먼저 보는 문제`, `화면에 옮길 기준`, `체크리스트로 바꿀 항목`, 그리고 직전 4개 잠금셋도 신규 글에서는 쓰지 않습니다. 이 표의 3개 외에는 모두 위 3개 중 하나로 흡수해 씁니다.

## SERVICE 출력 형식 — v2, 누적 글 호환용

> **2026-05-24 이후 신규 글은 위 v3 본문 형식을 따른다.** 이 절은 누적 글 호환을 위해 남겨두는 v2 형식 설명이다.

SERVICE 글은 외부 서비스의 화면·정책·전환·시장 변화를 설명합니다. `요약`은 원문 전체 핵심을 불릿 리스트로 정리하고, `매거진 인사이트`는 **우리(CTTD 에이전시)가 클라이언트 회의에 가져갈 적용 가설**로 바꿉니다. 각 회차는 기사 나열로 끝내지 말고 운영 맥락(이번 주 모니터링 범위·채택한 TOP·수집했지만 제외한 것)이 함께 읽히게 정리합니다.

회차 앞머리의 운영 메모는 `## Service` 바로 아래 단락으로 씁니다. **`###` 중간 헤더(`### 이번 주 모니터링 범위`, `### 채택한 TOP 항목` 등)는 사용하지 않습니다.** 레거시 파서([scripts/notion/report_parser.py](../scripts/notion/report_parser.py))가 `### ...`를 카테고리로 해석해 그 아래 `#### 01.` 항목들의 categoryKey를 덮어쓰기 때문입니다.

권장 형식:

```markdown
## Service

이번 주 Service 모니터링 범위는 {{관심사 축}}이며 {{확인 플랫폼}}을 중점적으로 봤습니다. {{이번 주 포인트}}.

#### 01. [플랫폼] 제목
```

`수집했지만 제외한 것`은 `## 수집했지만 제외한 것`(영역 무관 공통 섹션) 또는 영역별 단락으로 둡니다. 영역 안에서는 `### 수집했지만 제외한 것`을 쓰지 않습니다.

```markdown
##### 요약

- 핵심 변화: 무엇이 새로 등장/사라졌는가. (의무, 첫 불릿. 이 불릿이 곧 `핵심 인용` 메타 fallback)
- 근거 데이터: 수치·기간·범위 중 최소 1개. (의무, 둘째 불릿. "거래액 +47% · 2026년 4월 자사 발표" 형식)
- 서비스 맥락: 이 브랜드가 왜 지금 이걸 했는지. (의무)
- 사용자 행동 변화: 무엇이 줄거나 늘었나. ('변경 전→후'를 흡수)
- 화면·플로우 단서: 어디서·어떻게 보이는지. (의무, 디자이너용 위치 단서)
- 누가·언제: 발표자·발표일·적용 범위. (옵션)

##### 매거진 인사이트

> 이 변화의 의미를 압축한 한 문장 (예: "큐레이션 진입점을 카테고리에서 편집 테마로 옮긴 사례")

###### 이 변화가 클라이언트 사업에 닿는 지점
> 어느 종류의 클라이언트(패션 커머스·식품 D2C·핀테크 등)에서 어떤 사업 결정이 흔들리는가?

###### 우리가 제안할 수 있는 액션 가설
> 우리 에이전시가 어떤 종류의 클라이언트에게 어떤 화면·정책·기획을 제안할 수 있는가?

###### 우리 클라이언트 점검 질문
> 클라이언트 미팅에서 제안 직후 우리가 던질 한 문장. 의사결정자가 즉답할 수 있는 형태여야 한다.
```

SERVICE 작성 기준:

- `요약`은 위 6개 슬롯 골격에 맞춰 작성합니다. 첫 두 불릿(`핵심 변화` / `근거 데이터`)은 반드시 그 콘텐츠 요건을 만족해야 합니다.
- 각 SERVICE 항목은 `무엇이 바뀌었는가`, `어느 클라이언트 사업에 닿는가`, `우리 에이전시가 어떤 액션으로 제안할 수 있는가`까지 이어져야 합니다.
- `핵심 변화`는 1줄. 제목을 다시 풀어쓰는 표지 문장이 아니라 무엇이 새로 등장/사라졌는지 그 자체를 담습니다.
- `근거 데이터`는 원문에서 기간과 출처가 확인될 때만 씁니다. 없으면 첫 두 불릿 의무 미달이므로 후보에서 빠집니다.
- `이 변화가 클라이언트 사업에 닿는 지점`은 직전 v1의 `이 업데이트가 노리는 것`을 **클라이언트 시점**으로 재정의한 슬롯입니다. "이 사례가 어느 클라이언트 유형의 어떤 사업 의사결정에 직접 영향?"으로 답합니다.
- `우리가 제안할 수 있는 액션 가설`은 직전 v1의 `설계 관점에서 짚을 점`을 **에이전시 제안 시점**으로 바꾼 슬롯입니다. 화면·정책·기획 중 우리가 시안·전략으로 가져갈 액션을 1-2개 구체적으로 씁니다.
- `우리 클라이언트 점검 질문`은 미팅에서 제안 직후 던질 한 문장. "우리 서비스" 화법은 쓰지 않고 "**클라이언트사의 ~화면/지표/기획**"으로 씁니다.

## DESIGN 출력 형식 — v2, 누적 글 호환용

> **2026-05-24 이후 신규 글은 위 v3 본문 형식을 따른다.** 이 절은 누적 글 호환을 위해 남겨두는 v2 형식 설명이다.

DESIGN 글은 기능 출시처럼 억지로 `변경 전/후`를 맞추지 않습니다. 실제 화면, 표현 방식, 레이아웃, 브랜드 톤, 제작 흐름을 중심으로 씁니다.

```markdown
##### 요약

- 핵심 표현: 원문에서 인상적으로 다루는 사실/이미지/사례 (의무, 첫 불릿)
- 적용 맥락: 어떤 화면·매체·브랜드·룩북에 옮길 수 있는지 (의무)
- 관찰 가능한 패턴: 색·타이포·레이아웃·모션 중 반복 관찰된 디자인 패턴 (의무, 디자이너 인용용)

##### 디자인 인사이트

> 저장할 이유를 압축한 한 문장 (예: "차분한 톤의 신선식품 브랜딩 — 식품 D2C 시안에 인용")

###### 이 표현이 어울리는 클라이언트 톤
> 어떤 종류의 클라이언트(패션·뷰티·식품·콘텐츠 등)에서 어떤 톤·온도의 브랜드·캠페인·페이지에 어울리는가?

###### 우리 시안에 옮길 때 가져올·다듬을 요소
> 색·타이포·모션·레이아웃·컴포넌트 중 클라이언트 시안에 그대로 가져올 부분과 클라이언트 톤에 맞게 다듬어야 할 부분은?

###### 점검 질문
> 다음 클라이언트 시안 또는 운영 페이지 검토에 바로 대입할 한 문장 질문.
```

DESIGN 작성 기준:

- 본문 `요약`은 위 3개 슬롯에 맞춰 작성합니다. 원문에 없는 적용처나 해석을 넣지 않습니다.
- `핵심 표현`은 원문에서 가장 시각적으로 인상에 남는 사실 한 가지를 담습니다.
- `이 표현이 어울리는 클라이언트 톤`은 직전 v1의 `이 표현이 노리는 것`을 **클라이언트 톤 시점**으로 바꾼 슬롯입니다. 추상적인 "어떤 인상"보다 "**식품 D2C 봄 캠페인 톤**", "**핀테크 안정·신뢰 톤**" 같은 클라이언트 유형 + 결을 같이 적습니다.
- `우리 시안에 옮길 때 가져올·다듬을 요소`는 색상, 타이포그래피, 이미지·영상 연출, 모션, 컴포넌트, 정보 위계, 브랜드 일관성 중 검수할 기준을 두 갈래(가져올 것·다듬을 것)로 씁니다.
- `점검 질문`은 클라이언트 시안·운영 페이지 리뷰에서 바로 던질 수 있는 질문으로 씁니다.

## DEV 출력 형식 — v2, 누적 글 호환용

> **2026-05-24 이후 신규 글은 위 v3 본문 형식을 따른다.** 이 절은 누적 글 호환을 위해 남겨두는 v2 형식 설명이다.

DEV 글은 구현, 접근성, 브라우저 QA, 컴포넌트, 배포 검증에서 무엇을 확인해야 하는지 보여줘야 합니다.

```markdown
##### 요약

- 원문에서 확인한 구현/검증/운영 포인트
- 기능명, API/속성, 브라우저 조건, 제한점, 검증 방법 중 하나 이상을 포함

##### 매거진 인사이트

###### 이 변화가 우리 프로젝트에서 줄이는 작업
> 이 표준·도구·API·환경설정은 우리(CTTD 퍼블리셔) 클라이언트 프로젝트의 어느 작업 단계를 줄이거나 대체하는가?

###### 클라이언트 프로젝트에 적용할 때 짚을 점
> 어떤 종류의 클라이언트 프로젝트(콘텐츠 D2C·서비스 SaaS·정적 마이크로사이트 등)에 적용할 수 있고, 그때 어떤 브라우저·접근성·빌드 환경 검증이 필요한가? 같이 보면 좋은 기술이 있으면 이 섹션 마지막 1-2줄로 정리.

###### 점검 질문
> 현재 진행하거나 곧 시작할 **클라이언트 프로젝트의 마크업·CSS·환경설정**에 바로 대입할 수 있는 한 문장 질문.
```

DEV 작성 기준:

- 용어를 별도 섹션으로 풀이하지 않습니다. 일반 독자가 바로 이해하기 어려운 제품명·도구명·약어가 있을 때는 `요약` 첫 등장 위치에서 괄호로 풀어 설명합니다(예: `Radix UI(접근성 중심의 headless UI primitive 라이브러리)`).
- `요약` 불릿은 원문에서 확인한 구체 사실을 포함해야 합니다. "~를 소개합니다", "유용합니다" 같은 빈 문장은 실패입니다.
- 릴리즈/문서라면 기능명, 도구명, API/속성, 브라우저·접근성·성능 조건, 수치, 제한점, 검증 방법 중 하나 이상을 넣습니다.
- 블로그/오피니언 글이라면 작성자의 핵심 주장, 근거 사례, 비교 대상, 실무 판단 기준을 분리합니다.
- `이 변화가 우리 프로젝트에서 줄이는 작업`은 우리(CTTD) 퍼블리셔가 새 클라이언트 프로젝트 시작 시 줄이는 작업 단계를 구체적으로 1-2개 적습니다.
- `클라이언트 프로젝트에 적용할 때 짚을 점`은 어떤 종류의 클라이언트 프로젝트에 어울리는지를 먼저 적고, 적용 시 점검할 기술 조건을 이어 씁니다. 같이 보면 좋은 기술은 이 섹션 마지막에 1-2줄로 흡수합니다.
- code 스타일은 실제 코드성 표현에만 씁니다. 기능명, 제품명, 한국어 UI 문구, 강조 문장에는 쓰지 않습니다.

## 카테고리별 보강 기준

상세페이지는 같은 형식 안에서도 카테고리별로 읽을거리가 달라야 합니다. 아래 기준 중 해당 이슈에 가장 맞는 1-2개만 반영합니다.

### Service / fashion

- 브랜드관, 룩북, 카테고리 홈, 오프라인 매장, 찜/재입고처럼 `발견 → 저장 → 재방문` 흐름이 어떻게 이어지는지 봅니다.
- 할인보다 큐레이션 구조, 스타일 문맥, 브랜드 스토리, 저장 이후 알림/재방문 장치를 우선 설명합니다.
- 오프라인 이슈는 매장 규모보다 온라인 행동이 매장 이후 어떻게 회수되는지를 봅니다.

### Service / platform

- 로컬, 커뮤니티, 콘텐츠, 리서치, 검색/추천처럼 여러 참여자를 연결하는 구조를 봅니다.
- 리뷰, 후기, 프로필, 추천, 알림, 온보딩, 신고/검수 같은 신뢰 장치가 화면에서 어떻게 설명되는지 봅니다.

### Service / fintech

- 결제, 송금, 정산, 포인트, 캐시, 회비, 금융 조건처럼 돈의 흐름을 사용자가 오해하지 않게 만드는 UX를 봅니다.
- 혜택 총액보다 적용 조건, 보상 시점, 실패/취소/환불 상태, 수수료나 회비 회수 판단을 설명합니다.

### Service / ecommerce

- 멤버십, 무료배송, 페이백, 쿠폰, 리뷰, AI 검색처럼 `구매 전 불안`과 `결제 직전 계산 부담`을 낮추는 장치를 봅니다.
- AI 추천/검색은 답변 생성보다 비교 기준, 추천 근거, 상품 카드 연결, 필터 재조정 흐름을 우선합니다.

### Service / department_store

- VIP, 선물, 픽업, 예약, 오프라인 재고, 행사 동선처럼 온라인과 매장 경험이 어떻게 분담되는지 봅니다.
- 프리미엄 경험은 예약 확정, 혜택 적용, 매장 방문 전후 알림 같은 상태값이 명확한지 설명합니다.

### Service / beauty

- 피부 진단, 성분 비교, 리뷰, 랭킹, 듀프, 개인화 추천처럼 `신뢰 근거`가 화면에서 어떻게 설명되는지 봅니다.
- 글로벌/오프라인 확장은 상품 수출보다 현지 사용자가 처음 신뢰를 얻는 접점을 봅니다.

### Service / book_content

- 이어보기, 책갈피, 로그인 복구, 구독/소장/대여 결제, 추천 홈처럼 `중단 후 복귀`와 `콘텐츠 소유감`을 봅니다.

### Design

- 도구 소개보다 제작 순서, 승인 흐름, 브랜드 가이드 적용, 디자인 시스템과의 충돌, 최종 편집 가능성을 봅니다.
- AI 디자인 이슈는 결과물이 예쁜지보다 누가 검수하고, 어떤 원본/권리/컴포넌트 규칙을 기준으로 통과시키는지 설명합니다.

### DEV

- 릴리즈 소개보다 적용 조건, 영향을 받는 화면, 브라우저/런타임 호환성, 테스트와 롤백 기준을 봅니다.
- 브라우저 업데이트는 새 API 나열보다 다음 분기 컴포넌트 QA 체크리스트로 바꿉니다.

## 유익한 정보 구성

각 상세페이지는 아래 4가지 정보가 구분되어야 합니다.

- 확인된 사실: 원문에서 확인한 날짜, 기능, 범위, 수치, 제한
- 해석: 이 변화가 왜 지금 나왔고 어떤 흐름과 연결되는지
- 적용 기준: 우리 서비스에서 어떤 화면, 정책, 컴포넌트, 운영 규칙을 점검해야 하는지
- 주의점: 원문에서 확인되지 않은 수치, 과장하면 안 되는 효과, 도입 전 필요한 조건

본문에 별도 표를 만들 필요는 없지만, 문단 안에서 이 네 가지가 섞여 흐려지지 않게 씁니다.

## 설계 관점 작성 지침

`설계 관점`은 매거진 인사이트의 핵심 섹션입니다. 이 영역은 “이 기능이 생겼다”가 아니라 “이 변화에서 어떤 설계 판단을 읽어야 하는가”를 보여줘야 합니다.

반드시 포함할 관점:

- 화면 위계: 사용자가 가장 먼저 봐야 할 정보, CTA, 보조 정보의 우선순위
- 정보구조: 홈, 상세, 목록, 검색, 찜, 멤버십, 로그인 이후 화면이 어떤 순서로 이어지는지
- 행동 흐름: 탐색, 비교, 저장, 알림, 결제, 재방문 중 어느 행동을 줄이거나 강화하는지
- 판단 근거: 추천, 혜택, AI, 멤버십, 콘텐츠 카드가 사용자를 설득하는 근거를 충분히 보여주는지
- 상태와 피드백: 적용됨, 저장됨, 보상 받음, 혜택 가능, 이어보기 가능 같은 상태가 화면에서 명확한지

쓰지 말아야 할 문장:

- “사용자 경험을 개선했다”처럼 결과만 말하는 문장
- “중요하다”, “좋은 사례다”처럼 설계 근거가 없는 평가
- 기사 본문, 보도자료, 앱 릴리즈 노트를 다시 요약하는 문장
- 매출, 성장, 성과를 UX 효과처럼 단정하는 문장

## JSON 섹션 스키마 (magazine.json 출력)

마크다운 `magazine-report.md`는 `scripts/notion/export_magazine_json.py`(레거시) 또는 `scripts/collect/store.mjs`(신규)에서 아래 JSON 섹션 구조로 변환되어 `public/data/magazine.json`에 저장됩니다. AI 편집 단계에서 직접 JSON을 출력할 때도 같은 스키마를 따릅니다.

### Service / Design 공통

```json
{
  "sections": [
    {
      "title": "요약",
      "className": "article-section is-bullet-summary",
      "prose": false,
      "blocks": [
        { "kind": "list", "html": "첫 불릿 = 글 전체 결론 한 줄" },
        { "kind": "list", "html": "이후 불릿 = 결론을 뒷받침하는 구체 사실 (기능명·범위·수치·화면 변화·작성자 주장 근거 등)" },
        { "kind": "list", "html": "원문 밀도에 맞게 필요한 만큼 추가 — 개수 제한 없음, 채움 불릿 금지" }
      ]
    },
    {
      "title": "매거진 인사이트",
      "className": "article-section is-deep-dive",
      "prose": true,
      "blocks": [
        { "kind": "quote", "html": "이 업데이트의 의미를 압축한 한 문장" },
        { "kind": "paragraph", "html": "리드 문단 (2-3문장)" },
        { "kind": "subhead", "html": "왜 지금 이 업데이트인가" },
        { "kind": "paragraph", "html": "..." },
        { "kind": "subhead", "html": "사용자는 무엇을 덜 해도 될까" },
        { "kind": "paragraph", "html": "..." },
        { "kind": "subhead", "html": "설계 관점" },
        { "kind": "paragraph", "html": "..." },
        { "kind": "subhead", "html": "점검 질문" },
        { "kind": "list", "html": "우리 서비스에 바로 대입할 질문 1" },
        { "kind": "list", "html": "우리 서비스에 바로 대입할 질문 2" }
      ]
    }
  ]
}
```

Design은 `title`을 `"디자인 인사이트"`로 두고 소제목 셋을 `왜 참고할 만한가 / 어디에 적용할 수 있을까 / 디자인 관점 / 점검 질문`으로 바꿉니다. DEV는 `매거진 인사이트` 소제목을 `왜 지금 이 업데이트인가 / 구현 관점 / 실무에 어떻게 적용할 수 있을까`로 두고, 필요하면 마지막에 `같이 보면 좋은 기술` subhead + list 블록을 둡니다.

용어 풀이가 필요하면 `요약` 불릿 안에서 괄호로 짧게 처리합니다(예: `Radix UI(접근성 중심 headless UI primitive)`). 별도 `용어 설명` 섹션은 두지 않습니다.

### 클래스명 규약

| className | Vue 렌더 | 용도 |
|-----------|----------|------|
| `article-section is-bullet-summary` | `<ul class="bullet-summary-list">` | `요약` 섹션 (불릿 리스트, 자체 완결 요약 원칙 적용) |
| `article-section is-deep-dive` (`prose: true`) | `<div class="section-prose">` + 블록별 렌더 | 인사이트 섹션 (quote/subhead/paragraph/list 혼합) |
| `article-section is-cluster-member` | 클러스터 멤버 카드 | 같은 주제 묶음 카드 (자동 생성) |
| `article-section is-related-service` | 관련 서비스 정보 | `related-service.mjs`가 자동 추가 |

### 블록 종류 (`block.kind`)

- `list` — 불릿 리스트 항목. `is-bullet-summary` 안에서는 자체 완결 요약 불릿, `is-deep-dive` 안에서는 점검 질문 항목.
- `quote` — 인사이트 리드 문장. 영역별 인사이트 섹션의 첫 블록으로만 사용합니다.
- `subhead` — 인사이트 안의 H6 소제목. 위의 잠금 소제목 셋만 허용합니다.
- `paragraph` — 일반 문단.

이 4종 외 다른 `kind`는 추가하지 않습니다.
