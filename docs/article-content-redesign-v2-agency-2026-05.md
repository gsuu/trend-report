# 상세페이지 내용 v2 — 에이전시 관점 재정의 회의록 (2026-05-24)

> CTTD가 **자체 서비스를 만드는 회사가 아니라 여러 클라이언트사의 프로젝트를 수주받아 진행하는 디지털 에이전시**라는 사실이 명시되면서, 1·2·3번 회의에서 정한 매거진 시스템 전반을 **"우리 회사 적용"** 가정에서 **"우리 에이전시 직원이 클라이언트 회의·시안·구현에서 인용·제안"** 시점으로 재정의한다. 직전 결과를 깨도 좋다는 사용자 허락 하에 진행.

## 참석자 — 에이전시 직원 + 클라이언트 페르소나

이번 회의는 **에이전시 내부 담당자** 4명과 **외부 클라이언트 페르소나** 3명, 편집장·시스템 운영자가 함께 한다. 직전 회의들의 페르소나(시니어 PM·비주얼 디자이너·퍼블리셔)는 모두 **CTTD 직원**으로 재해석된다.

| 역할 | 정체 | 본 회의에서 보는 관점 |
|---|---|---|
| 편집장 | CTTD 매거진 운영자 | 7번째 회의 진행 |
| **CTTD 시니어 기획자** | 우리 에이전시 PM·전략 담당 | "이 글을 어느 클라이언트 회의에 들고 갈까" |
| **CTTD 비주얼 디자이너** | 우리 에이전시 UIUX·브랜드 디자이너 | "이 시안 작업할 때 어디서 인용할까" |

## 컨텍스트 정정 — CTTD = 에이전시 (회의 시작 전 합의)

**편집장**: 1·2·3번 회의는 묵시적으로 "독자가 자기 회사 서비스에 적용한다"는 전제로 짜였습니다. 그러나 우리는 자체 서비스를 만드는 회사가 아니라 **여러 클라이언트사의 프로젝트를 수주받아 디지털 산출물을 만드는 에이전시**입니다. 이 차이는 단순한 라벨이 아니라 **모든 글의 시점·문체·메타·잠금셋 슬롯명**에 깔린 가정을 모두 흔듭니다.

**CTTD 시니어 기획자**: 솔직히 직전 회의에서 SERVICE 잠금셋 마지막 슬롯을 "우리 클라이언트 점검 질문"으로 정한 건 무의식 중에 이미 이 방향을 향하고 있었어요. 다른 슬롯도 같은 어조로 맞춰야 시스템 일관성.

**클라이언트 PO (A)**: 저희에게 에이전시가 트렌드 자료를 들고 와서 "이렇게 하셨던 토스가 멤버십 혜택을 이렇게 바꿨고, 거기서 우리 다음 분기에 점검할 게 두 가지입니다"로 말해주면 가장 좋습니다. **사례 → 우리 회사 적용 가설 → 점검 질문** 3단 구성.

**시스템 운영자**: 이 컨텍스트는 `AGENTS.md` 최상단과 `CLAUDE.md`에 **"About CTTD"** 절로 박아야 미래 작업이 헷갈리지 않습니다.

**합의 (회의 본론 시작 전)**:
- CTTD = 디지털 에이전시. 자체 서비스를 만들지 않고 여러 클라이언트사 프로젝트를 수주받아 진행.
- 모든 매거진의 1차 독자는 **CTTD 직원**(기획자·디자이너·퍼블리셔).
- 글의 **사용 시점**은 우리 직원이 클라이언트 회의·시안·구현에서 인용·제안하는 순간.
- 본문은 항상 "사례 정리 → 클라이언트 적용 가설 → 점검 질문" 3단 흐름으로 수렴해야 한다.

## 안건 1. 직군 매핑은 유지하되 "**사용처**" 컬럼을 명시한다

**편집장**: service=기획자, design=디자이너, dev=퍼블리셔는 그대로 둡니다. 다만 **그 직군이 우리 에이전시 내부 직군**이라는 점, 그리고 **사용처가 외부 클라이언트 프로젝트**라는 점을 라벨에 같이 박습니다.

**CTTD 비주얼 디자이너**: 헤더 칩에 "Design · 디자이너"로만 띄우면 "내 디자인에 쓴다"로 읽힙니다. "Design · 디자이너 → 클라이언트 시안" 같은 식이 명료해요. 다만 칩 폭이 한정적이라 어려우면 hover/aria로.

**CTTD 퍼블리셔**: 구독 모달에는 "마크업·CSS·인터랙션 → **클라이언트 프로젝트 구현**" 처럼 노출하면 좋겠습니다.

**클라이언트 페르소나 B (금융)**: 외부에서 매거진을 보는 일은 거의 없겠지만, 만에 하나 본다면 "이 에이전시가 우리에게 어떤 직군으로 붙는지" 한눈에 보이는 게 신뢰감에 도움됩니다.

**결론**:
- 헤더 칩은 직군 라벨만 유지(공간 한정), aria-label·hover tooltip·구독 모달에 **사용처 보조 문구** 추가.
- AGENTS.md의 Audience↔Job Mapping 표에 **사용처** 컬럼 추가:
  - service → 기획자 · 클라이언트 전략·서비스 제안
  - design → 디자이너 · 클라이언트 시안·브랜드 작업
  - dev → 퍼블리셔 · 클라이언트 프로젝트 구현

## 안건 2. SERVICE의 1차 사용 시점은 "**클라이언트 의사결정자 미팅**"이다

**CTTD 시니어 기획자**: SERVICE 글이 다루는 정보는 시장·전략·신사업·플랫폼 변화입니다. 우리 기획자가 이걸 그대로 적용하는 게 아니라, **클라이언트사 의사결정자(CEO/PO/사업 리드)에게 분기 제안할 때 인용**합니다.

**클라이언트 PO (A)**: 정확히 그렇습니다. 우리 회사 전략 회의에서 "오늘의집은 144종 큐레이션을 로컬 테마로 묶었습니다. 우리 시즌 기획전도 같은 편집 프레임을 시도할 수 있을까요?" 식으로 에이전시가 제안하면 좋습니다.

**클라이언트 페르소나 B (금융)**: 우리 분야는 의사결정 속도가 느려서, 사례 1건이 우리 분기 제안에 갈 때까지 **수치·기간·발표 주체·제도적 맥락**이 다 받쳐줘야 임원 보고가 됩니다. 단순 "도입했다"로는 부족.

**CTTD 시니어 기획자**: 그러면 SERVICE 잠금셋도 "우리 클라이언트 점검 질문"이 마지막에 오는 게 맞지만, 앞 슬롯은 **"클라이언트의 어떤 사업 결정에 영향?"** + **"우리가 어떤 액션으로 제안할 수 있는가"** 두 개로 다시 짤 필요가 있습니다.

**결론**:
- SERVICE 잠금셋을 **에이전시 시점**으로 다시 정의:
  1. `이 변화가 클라이언트 사업에 닿는 지점`
  2. `우리가 제안할 수 있는 액션 가설`
  3. `우리 클라이언트 점검 질문`
- 본문 어조도 "우리 결제 화면" → "**클라이언트 결제 화면**" 어조로 표준 보정.

## 안건 3. Design은 "**우리 시안 작업에 인용**"하는 시점이다

**CTTD 비주얼 디자이너**: Design 글 1차 사용 시점은 "**클라이언트 브랜드·UX 시안 작업할 때 인용**"입니다. Mobbin/Awwwards/디스콰이엇 같은 발견 채널을 우리가 매일 보지만, 매거진의 가치는 그걸 **"이번 클라이언트 톤에 어울리는 표현 사례"** 로 정리해 두는 데 있습니다.

**클라이언트 페르소나 C (식품 D2C)**: 저는 디자이너 출신이고 의사결정 빠른 편이라, 에이전시가 "이번 시즌 캠페인은 GS25 X 산리오 톤이 아니라 컬리의 '늘신선' 같은 차분한 톤이 더 맞다"고 사례로 보여주면 바로 결정합니다.

**CTTD 비주얼 디자이너**: 그러면 Design 잠금셋도:
1. `이 표현이 어떤 클라이언트 톤에 어울리나`
2. `우리 시안에 옮길 때 가져올 요소·다듬을 요소`
3. `점검 질문` (다음 시안 또는 운영 페이지에 바로 대입)

**결론**:
- Design 잠금셋을 에이전시 시점으로 다시 정의:
  1. `이 표현이 어울리는 클라이언트 톤`
  2. `우리 시안에 옮길 때 가져올·다듬을 요소`
  3. `점검 질문`

## 안건 4. DEV는 "**우리 퍼블리싱 작업에 적용**"하는 시점이다

**CTTD 퍼블리셔**: DEV는 변화가 가장 적습니다. 우리는 어차피 코드·환경설정을 직접 다루니까 "내 작업 vs 클라이언트 작업" 구분이 흐립니다. 다만 **"이 코드 패턴은 어떤 종류의 클라이언트 프로젝트에 가져갈 수 있는가"** 는 명시되면 좋습니다. 예: "11ty 정적 사이트 빌드 패턴 — 콘텐츠 중심 D2C 브랜드 사이트에 적합".

**CTTD 시니어 기획자**: 결과적으로 모든 카테고리가 같은 시점 보정 — 사용처 정보가 한 줄 추가될 뿐.

**결론**:
- DEV 잠금셋:
  1. `이 변화가 우리 프로젝트에서 줄이는 작업`
  2. `클라이언트 프로젝트에 적용할 때 짚을 점`
  3. `점검 질문`

## 안건 5. 신규 메타 — `클라이언트 적합` (적용 가능 클라이언트 유형)

**클라이언트 PO (A)**: 에이전시 매거진의 검색·발견 1순위 질문은 항상 **"이 글 어느 클라이언트 미팅에 들고 갈까?"** 입니다. 그러면 글마다 **`클라이언트 적합` 메타**가 있으면 좋겠습니다.

**CTTD 시니어 기획자**: 예를 들어 "오늘의집 늘신선 론칭" 글이라면 `클라이언트 적합: 식품 D2C · 라이프스타일 커머스 · 신선식품 운영`. 한 글에 2~4개. Explore 패널 칩 그룹에도 추가 가능.

**시스템 운영자**: 메타 키 `클라이언트 적합` 신설. 명시 안 되면 fallback — `category`와 `brandNormalized`에서 자동 유추(예: 카테고리가 fashion이면 "패션 커머스" 추가).

**클라이언트 페르소나 B (금융)**: 클라이언트 유형 태그가 너무 많으면 노이즈. **표준 키워드 셋**(패션 커머스 · 뷰티 커머스 · 식품 D2C · 라이프스타일 커머스 · 핀테크 · 콘텐츠 플랫폼 · 마켓플레이스 · O2O · B2B SaaS 등 10~15개) 안에서만 고르는 게 좋습니다.

**결론**:
- 메타 `클라이언트 적합` 신설. 표준 키워드 셋 정의.
- 사이트 hero meta-row에 작은 라벨로 노출. Explore 패널에도 칩 그룹 추가.

## 안건 6. 회의 질문(`meeting_question`)의 의미 재정의

**편집장**: 직전 회의에서 `meeting_question`을 "SERVICE 글 의무"로 박았는데, 이게 **누가 누구에게 던지는 질문**이었는지 다시 정합니다.

**CTTD 시니어 기획자**: 이제부터는 **"우리가 클라이언트 회의에서 제안 직후 던지는 질문"**. 예: "지난 분기 우리 결제 화면 개편 이후, 멤버십 가입자의 첫 결제 완료율은 어떤 변화가 있었나요?" 같은 형식.

**클라이언트 PO (A)**: 좋습니다. 그런 질문이 우리에게는 "이 에이전시가 우리 사정을 안다"는 신호가 됩니다.

**결론**:
- `meeting_question` 작성 기준 보정: "**우리(에이전시)가 클라이언트 의사결정자에게 제안 직후 던질 한 문장 질문**".
- 사이트 라벨은 `💬 클라이언트에게 묻기` 그대로(이미 정합).
- 작성 표준 문서·writer 프롬프트 어조 정정.

## 안건 7. `핵심 인용` 박스의 의미 재정의

**CTTD 시니어 기획자**: 직전 회의에서 만든 `📌 슬라이드 인용` 박스도 같은 보정이 필요합니다. 우리 회사 슬라이드가 아니라 **클라이언트 제안 슬라이드**에 그대로 옮길 한 줄입니다.

**클라이언트 페르소나 C (식품 D2C)**: 슬라이드 한 줄이 의사결정에서 가장 큰 역할을 합니다. "오늘의집은 5월 25일까지 로컬 144종을 묶었다" 한 줄을 봤을 때 "그러면 우리 봄 캠페인은…" 머리가 바로 돕니다.

**결론**:
- `핵심 인용` 작성 기준 보정: "**클라이언트 제안 슬라이드에 그대로 옮길 1문장**".
- 라벨 그대로 `📌 슬라이드 인용`.

## 안건 8. `출처 검증` 박스 — 클라이언트 임원 질문에 대비

**CTTD 시니어 기획자**: 검증 박스가 가장 효과 큰 곳은 **금융·B2B 같은 깐깐한 클라이언트** 미팅에서 "이 자료 출처가 어디입니까?"에 즉답할 때입니다.

**클라이언트 페르소나 B (금융)**: 매체·저자·발행일·언어가 명시되어 있고, 우리 에이전시 측에서 "원문 본문 + 공식 트위터 교차 확인" 같은 메모까지 보여주면 회의장에서 안 흔들립니다.

**결론**:
- 박스 자체는 직전 회의 결과 그대로 유지(메타 4종 + 발행일).
- 작성 표준 문서에 "**클라이언트 깐깐 질문 대비용 박스**"라는 의도 명시.

## 안건 9. hero/구독 모달 어조·라벨 일괄 보정

**CTTD 비주얼 디자이너**: 헤더 칩의 직군 라벨 보조 문구가 현재 `subscribeHint`로 들어 있어요. 그걸 모두 **클라이언트 시점**으로 바꿉니다.

**시스템 운영자**:
- 현재 `AREA_JOB_LABELS`:
  - service: { role: "기획자", subscribeHint: "이커머스 기획·서비스" }
  - design: { role: "디자이너", subscribeHint: "UIUX 비주얼·브랜드" }
  - dev: { role: "퍼블리셔", subscribeHint: "마크업·CSS·인터랙션·정적 빌드" }
- 보정안:
  - service: subscribeHint: "**클라이언트 의사결정자에게 제안하는 기획자용**"
  - design: subscribeHint: "**클라이언트 시안·브랜드 작업하는 디자이너용**"
  - dev: subscribeHint: "**클라이언트 프로젝트 구현하는 퍼블리셔용**"

**결론**:
- AREA_JOB_LABELS의 subscribeHint를 위 안으로 교체.
- 구독 모달의 보조 문구도 동일 어조로.

### 합의 4가지

1. **CTTD = 에이전시**라는 컨텍스트를 시스템 최상단에 박는다. 미래 모든 에이전트가 이 가정 하에 동작.
